## 2. Что работает end-to-end прямо сейчас

**Сквозной путь ядра:** сценарий (WGS84) → проверка входа → метры → параметры съёмки по бортам → маска съёмки → подобласти → эшелоны → распределение → галсы по бортам → вылеты с обходом зон → расписание с разведением → краш-тест → план или отчёт → GeoJSON, KML, CSV на весь план и KML-задание на каждый борт.

**Сквозной путь входа (с 2026-09-24):** три файла KML заказчика + параметры задания → импорт с отчётом → сценарий. Через CLI и через API:

**Реальные сценарии стали выполнимы — две причины.** Первая — E3: зона манёвра разворачивается к соседнему галсу, а подобласть, которую иначе никто не снимет, отдаёт самолёту ядро и оставляет полосу у зоны; недоступное на `real_msk` сжалось с 1125 га до 126 га, на `real_nw` — до 27 га. Вторая — **площадка по рекомендации**: оставшиеся полосы лежат у круглых зон UUR332, UUR372 (`real_msk`) и UUR320 (`real_nw`), самолёту там не развернуться, а коптеру с исходных площадок не долететь. Система называла место площадки; она добавлена в параметры обоих сценариев («Восточная» и «Северо-западная», «по рекомендации») с одним Gemini, приписанным к ней: baseline сам борт к новой площадке не переводит. Эвристика E6 (с 2026-09-27) переводит: без приписки оба сценария у неё выполнимы (`real_msk` — 12,0 ч, `real_nw` — 35,5 ч), у baseline `real_nw` — нет. Приписка в параметрах оставлена, чтобы сравнение шло на одном сценарии.

`real_nw` — **отложенный** сценарий: настоящие зоны и препятствия заказчика к северо-западу от Москвы (16 зон, 297 препятствий), его же 549 островков в новой раскладке (`relayout-area`), четыре площадки, флот 2 × 201, 2 × Lite, 2 × 401, 6 × Gemini, GSD 4 см, ветер 7 м/с. Правило: **на `real_nw` алгоритм не настраивают** — настройка на `real_msk` и тестовых, итоговое сравнение с baseline (E12) показывается и на `real_nw`. Срок 41,9 ч при налёте 204 ч на 12 бортов (17 ч на борт при идеальной балансировке): летают 9 бортов из 12, западная площадка не используется — это точка отсчёта для `e6-allocate`.

**Почему цифры демо изменились 2026-09-24** (было: 237 подобластей, 98 вылетов, 16 ч 25 мин, ресурс 66 ч 7 мин). Перекрытия по умолчанию приведены к значениям производителя — 0,7 / 0,5 вместо наших 0,8 / 0,6 (решение владельца, долг №47). **6 (исходная постановка).** Шаги 2 и 3 E6, долги №25 и №53, плюс E12. Baseline не трогать (инвариант 8): новый алгоритм — отдельный модуль рядом, `core/allocate/`, выбирается в конвейере, baseline считается на тех же подобластях для сравнения.

- **Что показывают замеры baseline (2026-09-27).** `real_nw`: срок 41,9 ч при налёте 204 ч на 12 бортов — при идеальной балансировке 17 ч; летают 9 бортов, западная площадка не используется, у трёх Gemini ноль вылетов. `real_msk`: самолёты 201 летают по 10 ч до 11,7 ч, Gemini — от 0,3 до 5 ч. Демо: самолёты 1–3,6 ч, коптеры до 13,9 ч (долг №25). Причина везде одна: baseline делит подобласти по **площади** поровну между бортами, а не по времени, и даёт борту **одну** площадку по близости к его куску.
- **Шаг 2 — конструктивная эвристика «кто раньше освободится».** Очередь бортов по моменту готовности; готовому борту собирается следующий вылет: с его текущей площадки — ближайшие непокрытые подобласти, пока вылет помещается (`sortie_cost`); площадка посадки — та, что ближе к оставшейся работе (№29, непрерывность — `validate` уже проверяет). Борт, не приписанный в сценарии (`FleetUnit.site_id`), выбирает стартовую площадку сам — это снимает долг №53 (рекомендованная площадка без приписки коптера). В режиме «минимум ресурса» — вместо «кто раньше» борт с наименьшей ценой ресурса за гектар.
- **Шаг 3 — локальный поиск** с `seed`: перенос подобласти между вылетами, обмен, порядок облёта в вылете; критерий — режим сценария. Детерминированность (AGENT.md §8).
- **Скорость.** Сейчас на `real_msk` 2000 вызовов `sortie_cost` занимают 18 с из 20 — каждый собирает вылет целиком с маршрутизатором. Для поиска нужна дешёвая оценка (прикидка, как `_single_sortie_s` в `decompose.py`, плюс кеш перелётов) и точная сборка только у принятых вылетов.
- **E12.** Таблица «baseline против оптимизатора» по сроку и ресурсу в обоих режимах на всех сценариях; **`real_nw` — отложенный: на нём не настраивать**, показывать итог. CLI-команда сравнения, числа — в §2.
- Чего в задаче нет: пул вместо флота (задача 4), перестроение расписания (E14).

**7. `e10-web-upload` — загрузка файлов в вебе (долг №49, остаток №29).** Кнопки «Загрузить» в менеджере данных уже стоят, по одной на вид данных, и запоминают выбранный файл (`web/src/features/data/useUploads.ts`, пометка «не обработан»). Нужно:

- **Сценарий из слоёв.** Файлы области, зон и препятствий плюс параметры задания уходят в `POST /scenarios/import` (поля `area`, `zones`, `obstacles`, `params`). Параметры — загруженный JSON вида `scenarios/params/*.params.json` или, если его нет, параметры выбранного сценария (всё, кроме геометрии). Кнопка «Собрать сценарий» активна, когда есть область. Новый сценарий выбирается сразу, слои видны на карте до расчёта (`GET /scenarios/{id}/layers` уже есть).
- **Отчёт импорта** (`ImportReport`: прочитано, принято, исправлено, выброшено, вне области — по слою) — в менеджере под каждым видом, предупреждения — списком. Молча чинить и выбрасывать нельзя (№4).
- **Сценарий целиком** — JSON в `POST /scenarios`; отказ 422 показывается с полем и причиной, как в панели параметров.
- **Замена одного слоя** (например, только препятствий у выбранного сценария) требует нового маршрута: `POST /scenarios/import` ждёт все слои файлами KML, а геометрия сохранённого сценария лежит в JSON. Маршрут `POST /scenarios/{id}/layers/{kind}` — принять один KML, прочитать его тем же `core/geo/kml_import.py`, заменить слой и сохранить копией `<id>--custom`, как правки параметров. Расчётов в API нет — только вызов импорта ядра.
- **Исходники загруженного сценария.** `GET /scenarios/{id}/files` сейчас знает только сценарии манифеста (`scenarios/sources/manifest.json`). Сценарий, собранный из загруженных файлов, должен хранить их рядом (`storage/<id>/…`) — тогда менеджер данных покажет и их, со ссылкой на скачивание и отчётом импорта.
- Чего в задаче нет: рисования и правки геометрии (№8, №12), форматов кроме KML и JSON.

**За пределами плана, в порядке убывания ценности:** ЦМР (E1, P1) — её цена теперь измерена: 304 препятствия из 453 записаны отметкой над уровнем моря, и без рельефа план обходит их все как вдвое более высокие; руководство пользователя и пояснительная записка (E13); проверка `docker compose up` на чистой машине (долг №13); вкладка «Сравнение» — план против baseline и фронт Парето (E12, когда будет `e6-allocate`); справочник допущений в вебе из `GET /assumptions` — раздел «известные ограничения» (E13).

### 2026-09-27 — E6 шаг 3: эвристика видит расписание, локальный поиск, ветка `e6-local-search`

Задача 6а плана. Закрыт долг №54. Алгоритм по умолчанию сменился на `local_search` — планы всех сценариев другие (§2); baseline не менялся, его цифры те же.

- **Книга расписания** (`core/deconflict/schedule.py` → `ScheduleBook`, зона E14; правка — ради долга №54, он общий E6/E14). Поставленные вылеты: самый ранний старт (та же логика сдвигов, что была в `build_schedule`), откат к первым N вылетам, подобласти, из-за которых нельзя взлететь (`blocking_cells`: сближение траекторий над подобластью, зона манёвра, временная зона), районы, занятые чужими зонами манёвра на близкой высоте (`busy_footprint`) и временными зонами (`closed_footprint`). `build_schedule` работает через книгу; новый параметр `keep_order` — ставить вылеты в порядке списка. У baseline порядок прежний («первые вылеты всех бортов, потом вторые»).
- **Эвристика видит расписание** (`core/allocate/greedy.py`; `SortiePlacer` — протокол в распределении, `BookPlacer` в новом `core/deconflict/placer.py` — реализация над той же пробой модели полёта и тем же оракулом покрытия). Собранный вылет сразу ставится в книгу; борт освобождается по настоящей посадке. Сдвинут старт — вылет собирается заново: сначала без подобластей, из-за которых сдвиг; не помогло — без всего района, где в это время работают другие самолёты на той же высоте или действует временная зона; до `ALLOCATE_DELAY_RETRIES` раз. Берётся вариант с наибольшей площадью за время от готовности борта до посадки. В режиме «минимум ресурса» задержку не лечат — ожидание на земле ресурс не тратит, — но вылет, который из-за неё не успевает к сроку, укорачивается (тест дедлайна больше не держит минутного запаса). Расписание ставит итоговые вылеты в порядке эвристики и получает те же старты — это проверяет тест. Что ушло: на демо самолёты ждали первого старта 63 и 75 мин — **не соседа, а временной зоны ОРВД у южной площадки** (трассировка показала: пересечение участков съёмки с зоной в её окне); на `real_msk` самолёт больше не ждёт соседа 2 ч.
- **Проверено и отвергнуто в ходе задачи:** пересборка только без мешающих подобластей. Затравка «самая дальняя» снова вела самолёт в тот же район, конфликт сдвигался на соседний ряд подобластей: южный самолёт демо — четыре пересборки подряд с задержкой 61–63 мин. Поэтому вторая попытка — без всего занятого района, и она идёт в сравнение по площади за занятое время, а не заменяет вылет всегда (глобальное правило «обходить чужие районы» отвергнуто ещё в `e6-allocate`, долг №54).
- **Локальный поиск** (`core/allocate/search.py`, новый модуль). Ходы над готовым планом, каждый оценён настоящим расписанием: книга с откатом — заново ставится только хвост порядка после первого изменённого вылета (на `real_msk` оценка 0,05–0,5 с вместо 0,9 с полного расписания). Режим «минимум срока», над критическим вылетом: раздать его подобласти — все, половину, четверть последних по облёту — другим бортам (в последний вылет или новым; подобласть получает борт, который по оценке раньше её закончит; нижние границы `SortieBounds` отсекают безнадёжных до сборки); переставить его целиком борту, который раньше освободится; поставить его в очереди сразу за предыдущим вылетом своего борта (кто уступает при разведении, решает порядок постановки) или облететь в обратном порядке. Затем — оставить на земле борт с наименьшей снятой площадью (работа раздаётся остальным). В обоих режимах — растворить короткий вылет в последних вылетах бортов (ресурс, №23). Принимается лучший вариант хода по критерию режима: главный, при равенстве — второй; ходы хвоста, которые ничего не дали, не повторяются, пока хвост тот же. Предел — `ALLOCATE_SEARCH_MOVES` принятых ходов, не время: один сценарий — один план. Случайности нет, `seed` на поиск не влияет. Не сделано: обмен подобластями между вылетами и 2-opt внутри вылета.

### 2026-09-27 — E5: граф видимости на данных заказчика, ветка `e5-visibility-speed`

Третья задача плана (долг №48). Сценарий на файлах заказчика впервые посчитан целиком.

- **Что мерили.** На `real_msk` у графа эшелона 285 м 3942 узла, у высоты съёмки Gemini 255 м — 6347; прежний граф перебирал все пары (7,8 млн для 285 м) и спрашивал для каждой `prep(...).intersects` — 246 с. STRtree по частям геометрии — ещё медленнее, отрезки длинные и задевают много габаритов.
- **Что сделано** (`core/transit/routing.py`). Граф не строится: A* с расстоянием по прямой до цели считает рёбра узла, когда до него дошёл, и запоминает их. Дорогая проверка видимости достаётся только парам, которые могут лежать на кратчайшем пути вокруг отодвинутых областей: узел — выпуклая вершина (в вогнутой кратчайший путь не поворачивает), ребро касается контура в обоих концах (оба соседа узла по контуру — по одну сторону от ребра). Оба отбора — арифметика numpy. Для конца пути, лежащего в полосе отступа (конец галса у края буфера), отбор по касанию неверен — там проверяются все узлы; без этого первая версия возвращала прямую сквозь препятствие вместо обхода, и сверка с эталоном это поймала. Граф выбирается по высоте из кеша: перебор 547 препятствий на каждом из 42 тысяч вызовов стоил 15 с.

- **Сверка с прежним графом.** Все 1342 вызова маршрутизатора четырёх сценариев пересчитаны новым кодом: 169 путей стали длиннее на 0,1–4,1 м (на перелётах 0,5–4,4 км), короче или «прямой вместо обхода» — ни одного. Причина: прежний путь срезал хорду через 10-метровую полосу отступа, новый идёт по её краю, то есть дальше от препятствия. Метрики планов не сдвинулись (ресурс `medium` +0,1 мин).
