## 2. Что работает end-to-end прямо сейчас

**Ничего.** Исполняемого кода в репозитории нет.

Что есть фактически: `README.md`, `PROJECT_BRIEF.md`, `docs/architecture.md`, `docs/epics.md`, `AGENT.md`, `CLAUDE.md`, `docs/current_state.md`, `docs/external_sources.md`.

Чего нет: пакета `core/`, `api/`, `web/`, `data/vehicles.yaml`, `scenarios/`, `docker-compose.yml`, тестов, конфигурации сборки.

Ближайшая цель сквозного пути (по E0 + Фазе 1 архитектуры): полигон рисуется в браузере → отправляется в API → возвращаются маршруты → отрисовываются на карте → экспортируются в KML, открывающийся в стороннем ПО. До этой точки алгоритм не улучшается.

## 4. Принятые допущения

### 4.1 Ещё не перенесены в `core/assumptions.py`

Файл `core/assumptions.py` не создан (E0). Все допущения ниже переносятся в него при создании, каждое — с комментарием об источнике.

| Допущение | Основание |
|---|---|
| Направление ветра — метеорологическая конвенция (откуда дует) | Инвариант 4 брифа |
| Ветер — константа по всей области и на всех высотах, без профиля | Упрощение до ответа организаторов (вопрос 3) |
| Рельеф не учитывается, высоты — относительно точки старта | Опционально по ТЗ; в scope только при наличии времени (E4/E5) |
| Целевая функция оптимизации — `α·makespan + (1−α)·суммарный налёт` | Бриф §6, `docs/epics.md` E6 |
| Единая метрическая проекция на входе в `core`, WGS84 только на границах | Инвариант 1 брифа |

### 4.2 Ждут ответа организаторов

Ответы меняют объём эпиков E3, E4, E6. До получения — работаем по допущению, зафиксированному во второй колонке.

| Вопрос | Что дало ТЗ | Рабочее допущение |
|---|---|---|
| Точки взлёта задаёт пользователь или сервис подбирает сам? Нужны ли несколько вылетов одного борта со сменой батареи? | **Закрыт наполовину.** Раздел 2: «координаты взлётно-посадочных пунктов (произвольные)» — это вход, задаёт пользователь. Про смену батареи ТЗ молчит | Площадки задаёт пользователь; многовылетность **поддерживается** (E6, шаг 2) |
