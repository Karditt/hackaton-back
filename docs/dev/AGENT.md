## 1. Контекст и архитектурный инвариант

Сервис планирования и распределения беспилотных авиационных работ: по сценарию (область съёмки, тип съёмки и GSD, флот БВС, площадки взлёта-посадки, запретные зоны с высотами и временем, высотные препятствия, коридор высот, ветер) сервис **делит работу между бортами**, рассчитывает индивидуальные полётные задания и общее расписание и выгружает их в KML/GeoJSON. Выход — полный план или отчёт о невыполнимости с рекомендациями; частичных планов нет. Оптимизация — два режима: минимум срока и минимум ресурса техники при необязательном дедлайне (бриф §4.3).

Заказчик проверяет решение прежде всего **краш-тестом**: сближения бортов, залёты в запретные зоны, пролёты у препятствий (заказчик, №4). Любая правка оценивается в первую очередь по тому, не может ли она выпустить план с таким нарушением.

Архитектура — **модульный монолит с конвейером чистых стадий**:

```
Scenario ─▶ SurveyPlan ─▶ Decomposition ─▶ Allocation ─▶ Coverage ─▶ Schedule ─▶ Validation ─▶ Mission ─▶ Files
```

Подробно — бриф §2 и [`docs/dev/architecture.md`](architecture.md) §3.1. Сборка — `core/pipeline.py`.

Каждая стадия: типизированный вход → типизированный выход, **без состояния**, знает о соседях только через типы из `core/schemas.py`.

Границы слоёв:

```
web/    React + TS + Vite + Leaflet   ──REST+поллинг──▶  api/
api/    FastAPI, тонкий слой          ──импорт──────▶    core/
core/   чистый Python, НОЛЬ веб-зависимостей, собственный CLI
```

**Жёсткое правило:** `core` не импортирует ничего из `api` и `web`. Ядро запускается как `python -m core.cli` и живёт без веба. Это страховка на случай, если веб-слой отстанет.

Направление зависимостей строго одностороннее: `web → api → core`. Обратных стрелок нет ни одной.

### Куда класть новый код

- Новая физика полёта → `core/flight/`, константы → `core/assumptions.py`.
- Новый тип съёмки → строка в `data/survey_presets.yaml`; своя физика на тип съёмки не пишется (заказчик, №26).
- Новая метрика плана → вычисляется в `core/`, API только отдаёт готовое.
- Новая проверка безопасности → `core/validate/`, даже если та же логика уже есть в стадии, которая строит план. Валидатор не вызывает код стадий, которые он проверяет.
- Новый внешний источник данных → провайдер с кешем по образцу `core/terrain/`, стадии получают уже загруженные данные.

### Куда код класть **нельзя** (типичные ошибки)

- ❌ **Геометрические и физические расчёты в слое `api/`.** Это самая частая ошибка. API — транспорт: валидация запроса, вызов `core`, сериализация ответа. Если в хендлере появились `shapely`, `pyproj`, `numpy` или арифметика с координатами — расчёт написан не там.
- ❌ **Логика в компонентах `web/`.** Фронтенд рисует то, что вернул API, и не пересчитывает маршруты, длины и время самостоятельно.
- ❌ **Импорт `api` или `web` из `core`** — любой, включая «только для типов».
- ❌ **Дублирование схем.** Типы фронтенда генерируются из `core/schemas.py`, не пишутся руками.
- ❌ **Константы по месту использования** вместо `core/assumptions.py`.

## 3. Чек-лист инвариантов (проверять перед завершением работы)

Раздел 5 брифа в виде проверяемого списка. Код, нарушающий любой пункт, считается сломанным **независимо от того, проходят ли тесты**.

- [ ] **1. Вся геометрия — в метрической проекции.** WGS84 живёт только на границах системы: на входе из сценария и на выходе в экспорт. В `core` между границами — метры. Расчёты в градусах дают неверные расстояния и площади, и ошибка тихая.
- [ ] **2. `core` не знает про веб.** Ни одного импорта из `api`. Проверка: `python -m core.cli` отрабатывает при полностью отсутствующем `api/`.
- [ ] **3. `core/schemas.py` не изменён** — или изменён осознанно, с явной отметкой в `docs/dev/current_state.md` и перегенерацией TypeScript-типов (см. §4).
- [ ] **4. Направление ветра — метеорологическая конвенция (откуда дует).** Перепутанный знак даёт зеркальный план: галсы ложатся поперёк ветра, выполнимость проверяется не на том курсе. Обнаруживается только на демонстрации.
- [ ] **5. Ни одного магического числа** вне `core/assumptions.py`. Каждая константа там — с источником. Значение заказчика помечено «заказчик, №N» и не выдаётся за допущение команды.
- [ ] **6. Ни одной выдуманной ТТХ БВС.** Каталог — `data/vehicles.yaml` из официальных источников. Неизвестная характеристика помечается как пробел, а не заполняется правдоподобным числом. Вывод по явной формуле из документированных чисел допустим — с пометкой в `derived_fields`. ТТХ, заданные пользователем (правка модели каталога или своя модель), — вход, а не выдумка: они приходят в `Scenario.vehicles`, поля перечислены в `user_fields`, план предупреждает `catalog.user_vehicle`, каталог при этом не меняется (решение владельца, 2026-09-26).
- [ ] **7. Время вылета — сумма фаз, а не «длина маршрута / одна скорость».** Взлёт, набор, перелёт, галсы, развороты, ожидание, снижение, посадка — каждая со своей скоростью. На галсе — путевая скорость, которую держит автопилот. Отсечка заряда 20%. Ветер во время и расход не входит (заказчик, №45).
- [ ] **8. Baseline-алгоритм на месте.** Равномерное деление области не удалено, не «отрефакторено в ноль», доступно для сравнения.
- [ ] **9. Ни один выданный план не нарушает жёстких правил безопасности.** Траектория и зоны манёвра не пересекают запретные зоны в их высотах и окнах действия, не выходят за пространство и коридор высот, не подходят к препятствиям ближе допустимого; ни одна пара бортов не сближается ближе минимума разделения. Нарушение — невыполнимость, а не предупреждение. Независимый валидатор это подтверждает.
- [ ] **10. Нет частичных планов.** Область покрыта целиком — или результат объявлен невыполнимым с причиной и рекомендацией.

## 4. Правила работы с контрактом

`core/schemas.py` — единственная точка синхронизации между тремя параллельными потоками работы. Её правка ломает всех одновременно.

Порядок изменения схемы:

1. Убедиться, что изменение действительно необходимо, а не обходной путь вокруг чужой незавершённой работы.
2. Внести правку **аддитивно**, если возможно: новое опциональное поле со значением по умолчанию не ломает соседей, переименование поля — ломает.
3. Перегенерировать JSON Schema и TypeScript-типы для фронтенда (см. команду в [`.claude/CLAUDE.md`](../../.claude/CLAUDE.md)).
4. Записать в `docs/dev/current_state.md` → «Журнал изменений» **отдельной строкой с пометкой о правке контракта**: что изменилось, зачем, что может сломаться у соседей.
5. Прогнать тесты и CLI на всех сценариях из `scenarios/`.

Ломающее изменение схемы без отметки в `current_state.md` — дефект сам по себе, даже если код корректен.

## 5. Параллельная агентная работа

**Одна сессия — один эпик — одна ветка.** Ветка именуется по эпику: `e3-coverage`, `e6-allocate`.

- **Не трогай модули за пределами своего эпика.** Карта в §2 задаёт границы. Нужна правка в чужой зоне — опиши её в отчёте и в `current_state.md`, но не делай.
- **Нужен ещё не реализованный модуль — пиши заглушку**, а не блокируйся и не переписывай чужую зону.
  - Заглушка возвращает правдоподобные данные корректного типа из `core/schemas.py`.
  - Помечается явным `TODO(E<номер эпика>): заглушка, заменить на реальную реализацию`.
  - Заносится в раздел «Заглушки и временные решения» в `current_state.md` с указанием, какой эпик её закроет.
  - Заглушка **не должна молча выглядеть как настоящий расчёт**: логируй предупреждение или проставляй флаг в результате.
- **Конфликт границ** (два эпика правят один файл) — не разрешается «на месте»: фиксируй в `current_state.md` и оставляй решение команде.
- Коммить только свою зону. Побочные правки чужих файлов — в отдельный коммит с объяснением.

## 6. Обязательные шаги перед завершением задачи

Ни один из пунктов не пропускается, даже если изменение кажется тривиальным.

1. **Тесты** — `pytest` проходит полностью. Новый код стадии сопровождается тестами.
2. **Линтер и форматтер** — прогнаны, замечаний нет.
3. **CLI на тестовых сценариях** — `python -m core.cli` отрабатывает на **всех** сценариях из `scenarios/`, включая «злой». Не только на удобном.
4. **Чек-лист инвариантов из §3** — пройден по пунктам.
5. **`docs/dev/current_state.md` обновлён** — статус эпика, что работает, что заглушка, новые допущения, журнал изменений.
6. **Отчёт о работе** в формате §8.

## 7. Что запрещено делать самостоятельно

Требует явной задачи или решения команды:

- ❌ **Выдумывать технические характеристики БВС.** Источник каталога — `data/vehicles.yaml` и официальные страницы производителя. Нет данных — это пробел, фиксируемый в `current_state.md`, а не правдоподобное число. Числа, которые ввёл пользователь, — не выдумка команды: они живут в сценарии (`Scenario.vehicles`) и помечены, в каталог не попадают.
- ❌ **Добавлять зависимость молча.** Заказчик ограничений не ставит (№18), но каждая новая зависимость отмечается в `current_state.md` с одной строкой обоснования. Не берём то, что требует ключа или платной лицензии: жюри запускает решение само. Celery/Redis/RabbitMQ, обязательный PostGIS, тяжёлые UI-киты — не используем (бриф §3).
- ❌ **Ходить в сеть из стадии конвейера.** Онлайн-источники разрешены (№16), но только через провайдер с дисковым кешем (`core/terrain/`) и с понятной ошибкой при недоступности. Стадия получает уже загруженные данные и тестируется без сети.
- ❌ **Менять целевые функции оптимизации.** Режимы «минимум срока» и «минимум ресурса при дедлайне» и свёртка `α·T + (1−α)·R` зафиксированы в брифе §4.3. Изменение весов, слагаемых, нормировки или стоимости цикла взлёт-посадка — только по явной задаче.
- ❌ **Выдавать план с нарушением жёсткого правила** — даже с предупреждением уровня ОШИБКА. Такой результат — невыполнимость (инвариант 9).
- ❌ **Выдавать частичный план** (инвариант 10).
- ❌ **Удалять или отключать baseline-алгоритм.** Он всегда даёт результат и служит точкой сравнения, доказывающей эффективность решения.
- ❌ **Подключать OR-Tools как основу оптимизатора.** Заказчик не запрещает; это решение команды (бриф §3). Допустим как альтернатива для сравнения с собственной эвристикой.
- ❌ **Делать ввод и редактирование геометрии на карте** — заказчик это исключил (№8, №12). Геометрия приходит файлами.
- ❌ **Заменять поллинг на WebSocket** без отдельного решения.
- ❌ **Вводить авторизацию, роли, многопользовательский режим, миграции БД** — вне объёма, заказчик подтвердил (№15).

## 8. Требования к коду

**Типизация.** Все публичные функции стадий аннотированы. Границы стадий — только типы из `core/schemas.py`, не голые `dict` и не кортежи.

**Докстринги с единицами измерения.** У каждой публичной функции стадии — докстринг, явно называющий единицы: метры, секунды, радианы, м/с, Вт·ч, доля (0..1). Отсутствие единиц в докстринге функции, принимающей число, — дефект: именно на смешении градусов с радианами и км с метрами ломаются такие расчёты.

```python
def leg_duration(length_m: float, ground_speed_mps: float) -> float:
    """Длительность участка.

    Args:
        length_m: длина участка, метры (метрическая проекция).
        ground_speed_mps: путевая скорость, м/с (с учётом ветра).

    Returns:
        Длительность, секунды.
    """
```

**Детерминированность.** Любой недетерминированный алгоритм (локальный поиск, ALNS, перебор с рандомизацией) принимает `seed` и по умолчанию воспроизводим. Один и тот же сценарий с одним seed даёт побитово один и тот же план. Без этого невозможен бенчмарк и невозможна отладка на демонстрации.

**Никаких магических чисел** вне `core/assumptions.py`. Число в формуле расчёта, не являющееся математической константой самого выражения, — в `assumptions.py` с комментарием об источнике. Этот файл механически превращается в раздел «известные ограничения» документации, который требуется по ТЗ.

**Чистота стадий.** Стадия не пишет в глобальное состояние, не ходит в сеть, не читает файлы вне переданных ей путей, не зависит от порядка вызова.

**Понятные ошибки.** Невыполнимый сценарий — это отчёт о невыполнимости с причиной и рекомендацией (инвариант 10), а не тихий пустой результат, не частичный план и не падение по `IndexError`. Ошибка входных данных — самопересечение, недопустимое значение — отвергается при приёме с указанием места, а не чинится молча. Предупреждение (`warning`) — только для того, что план не ломает: запас по заряду, близость к пределу ветра, недосягаемая резервная площадка.

## 9. Расхождения между документами

Иерархия источников:

1. **Ответы заказчика** — [`docs/dev/customer_qa.md`](customer_qa.md). Действуют поверх ТЗ и поверх любых наших допущений.
2. **`docs/dev/PROJECT_BRIEF.md`** — источник истины по архитектуре. С редакции 2026-09-18 согласован с ответами заказчика.
3. **`docs/dev/architecture.md`, `docs/dev/epics.md`** — обоснования и состав работ. В редакции 2026-09-18 приведены в соответствие с брифом; прежние четыре расхождения (WebSocket, `api/schemas.py`, `core.plan`, модули вместо пакетов) сняты.

**Код и документы.** Каркас кода приведён к ответам заказчика (контракт v2, 2026-09-18). Оставшиеся расхождения — [`docs/dev/current_state.md`](current_state.md) §6. Пока пункт там не закрыт, правильное поведение описывают документы, а не код.

Обнаружил новое расхождение — не решай его молча: зафиксируй в `docs/dev/current_state.md` → «Известные проблемы и долги».

## 10. Формат отчёта о работе

Каждая завершённая сессия заканчивается отчётом такой структуры (он же — основа записи в `docs/dev/current_state.md`):

```markdown
## Эпик E<N> — <название>, ветка <branch>

### Что сделано
- <конкретно, по модулям; что теперь работает end-to-end, а что — на заглушках>

### Принятые допущения
- <допущение> — <почему; перенесено в assumptions.py / ждёт ответа организаторов>

### Что осталось незакрытым
- <пункт> — <почему: не в объёме эпика / блокирует другой эпик / не хватило данных>

### Новые обнаруженные пробелы
- <неизвестная ТТХ, расхождение в документах, неоднозначность в ТЗ, чужая зона, требующая правки>

### Контракт
- core/schemas.py: не изменён / изменён — <что именно и что может сломаться>

### Проверки
- pytest: <результат>
- линтер/форматтер: <результат>
- CLI на scenarios/: <результат по каждому сценарию, включая «злой»>
- чек-лист инвариантов §3: <пройден / расхождения>
```

Отчёт честный: «почти готово» — не статус. Если сквозной путь не работает, так и пишется.
