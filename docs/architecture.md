# Архитектура

Как устроено решение: слои, конвейер расчёта, модули, данные, запуск. Зачем
именно так и чего это даёт — [`explanatory_note.md`](explanatory_note.md);
программный интерфейс — [`api.md`](api.md).

## 1. Слои

```
web/    React + TypeScript + Vite + Leaflet   ──REST + поллинг──▶  api/
api/    FastAPI, тонкий слой (OpenAPI)        ──импорт─────────▶   core/
core/   чистый Python: shapely, pyproj, numpy, pydantic; собственный CLI
```

- **Ядро (`core/`)** — вся предметная логика: геометрия, модель съёмки и полёта,
  распределение, расписание, краш-тест, выгрузка. Не знает про веб: запускается
  как `python -m core.cli` и работает, даже если удалить `api/` и `web/`.
- **API (`api/`)** — транспорт: приём и проверка сценариев, фоновые задачи с
  поллингом, отдача результатов и файлов. Ни одного расчёта — только вызовы ядра.
- **Веб (`web/`)** — показывает то, что вернул API: карта, итог, расписание,
  парк техники, вопросы о плане. Маршруты, длины и время не пересчитывает.
  Геометрию на карте не рисует и не правит — она приходит файлами из ГИС.

Зависимости строго в одну сторону: `web → api → core`. Типы фронтенда
порождаются из контракта ядра (`core/schemas.py` → JSON Schema → TypeScript), а
не пишутся руками.

## 2. Конвейер расчёта

Каждая стадия — чистая функция: типизированный вход → типизированный выход, без
состояния; стадии знают друг о друге только через общий контракт
`core/schemas.py`. Сборка — `core/pipeline.py`.

```
Сценарий (WGS84)
  → проверка входа и перевод в метры (UTM)          core/geo
  → параметры съёмки по бортам                      core/survey
  → подобласти                                      core/coverage/decompose
  → эшелоны перелёта                                core/deconflict
  → распределение по вылетам                        core/allocate
  → галсы в подобластях                             core/coverage
  → вылеты: фазы полёта, обход зон                  core/flight, core/transit
  → расписание с 4D-разведением                     core/deconflict
  → краш-тест                                       core/validate
  → план или отчёт о невыполнимости с советами      core/advise
  → GeoJSON, KML, CSV (WGS84)                       core/export
```

Три свойства держатся по всему конвейеру:

1. **Метры внутри, WGS84 на границах.** Координаты переводятся в метрическую
   проекцию на входе и обратно — только в выгрузке: расчёты в градусах дают
   неверные расстояния, и ошибка тихая.
2. **Одна модель полёта.** Распределение оценивает вылет той же сборкой и
   ставит его в ту же книгу расписания, что дают итоговый план.
3. **Независимый краш-тест.** Проверка не вызывает код стадий, которые строили
   план, а заново проверяет готовые вылеты по жёстким правилам. Нарушение —
   невыполнимость, не предупреждение.

## 3. Модули ядра

| Модуль | Ответственность |
|---|---|
| `core/schemas.py` | Контракт: сценарий, стадии, план, расписание, отчёты |
| `core/assumptions.py` | Все константы и допущения, у каждого — источник; из реестра собирается раздел «известные ограничения» |
| `core/catalog.py`, `data/vehicles.yaml` | Каталог БВС Геоскан с источником у каждого числа; ТТХ пользователя поверх каталога |
| `core/geo/` | Проекции, мультиполигон, проверка геометрии, зоны с высотами и окнами действия, препятствия, маска съёмки, высота Солнца, импорт слоёв KML |
| `core/survey/`, `data/survey_presets.yaml` | GSD → высота, ширина захвата, шаг галсов, перекрытия по типам съёмки, путевая скорость при ветре |
| `core/coverage/` | Подобласти (островки, части крупных, полоса у запретного), галсы и зоны манёвра |
| `core/flight/` | Фазы полёта, развороты самолёта, расход заряда, дальность, 4D-траектория |
| `core/transit/` | Граф видимости с ленивым A*: перелёты в обход зон и препятствий |
| `core/allocate/` | Baseline, конструктивная эвристика, локальный поиск, порядок облёта, критерии режимов |
| `core/deconflict/` | Эшелоны, книга расписания, разведение бортов, переходы на высоте съёмки |
| `core/validate/` | Краш-тест |
| `core/advise/` | Причины невыполнимости, советы и их проверка расчётом |
| `core/export/` | GeoJSON, KML, расписание CSV, задания бортов, архив; сценарий обратно в слои KML |
| `core/hints.py`, `core/pareto.py`, `core/sites.py` | Вопросы о плане: сколько бортов к сроку, фронт «срок — ресурс», места площадок — прогонами конвейера |
| `core/sources.py` | Сборка сценария из слоёв и параметров; исходные файлы сценариев |
| `core/text.py` | Подписи для человека: режимы, фазы, борта, числа по-русски |
| `core/cli.py` | Командная строка: расчёт, пакетный прогон, сравнение, подсказки, импорт и выгрузка слоёв |

## 4. Производительность

- **Варианты распределения — в нескольких процессах** (до 4): две стратегии
  эвристики, несколько целевых сроков, доводка поиском. Результат от числа
  процессов не зависит — один сценарий даёт побитово один план.
- **Ленивый граф видимости**: рёбра считаются только у узлов, до которых дошёл
  поиск; на 547 препятствиях заказчика — сотые доли секунды на перелёт.
- Время: демо (~95 км², 10 бортов) — около 40 с, данные заказчика (245 км²,
  15 бортов) — около 5 минут при ориентире заказчика 30 минут.

## 5. Данные и хранение

- **Вход** — сценарий JSON или слои KML (область, зоны, препятствия, площадки) и
  параметры JSON; формат — [`input_formats.md`](input_formats.md).
- **Хранилище** — файлы, без базы данных: `storage/` (сценарии, загруженные
  исходники, парк техники, готовые планы — последние 30). В Docker —
  том `./storage`.
- **Выход** — обзор плана и задание каждого борта в KML (OGC 2.2, трек для
  Google Earth), GeoJSON, расписание CSV, архив; формат —
  [`export_format.md`](export_format.md).
- **Подложка карты** — OpenStreetMap (ODbL), атрибуция на карте.

## 6. Запуск и проверка

```bash
docker compose up                         # интерфейс :5173, API и OpenAPI :8000/docs
pip install -e ".[dev]" && pytest         # ядро, API и ~390 тестов, в том числе краш-тест на испорченных планах
python -m core.cli --batch scenarios/ -o out/
```

Два контейнера: `api` (Python 3.11, uvicorn) и `web` (Node, Vite с прокси `/api`
на сервис `api`). Внешних сервисов, ключей и платных лицензий нет.

## 7. Ключевые решения

| Решение | Почему |
|---|---|
| Модульный монолит с конвейером чистых стадий | Каждую стадию можно проверить отдельно и заменить; промежуточные стадии видны в `/jobs/{id}/result` |
| Своя эвристика с локальным поиском, а не общий решатель | Разведение в 4D, зоны манёвра, временные зоны и окна по Солнцу — в одной книге расписания, которую видит распределение |
| Baseline оставлен навсегда | Точка сравнения, которой измеряется эффективность оптимизатора |
| Фоновая задача и поллинг вместо брокера очередей | Однопользовательский сервис; меньше движущихся частей для запуска на чистой машине |
| Геометрия только файлами | Заказчик готовит данные в ГИС; рисование на карте исключено |
| ТТХ — только из документов производителя или от пользователя | Неизвестное число — пробел, а не правдоподобная выдумка; план говорит, какие числа расчётные |
