# GEOSCAN — архитектура проекта и порядок разработки

**Статус:** Proposed
**Контекст:** хакатон, ТЗ «Сервис планирования и распределения беспилотных авиационных работ»
**Решают:** вся команда (архитектуру фиксируем в первые часы и дальше не пересматриваем)

---

## 1. Вводные

### 1.1 Функциональные требования (сжато)
- Ввод сценария: область съёмки, тип съёмки, точки взлёта/посадки, флот БВС, NFZ, границы воздушного пространства, ветер.
- Расчёт покрытия галсами с учётом параметров сенсора.
- Распределение галсов между разнотипными БВС (multi-trip, multi-depot) по одному из двух критериев (makespan / суммарный налёт), с возможностью переключения.
- Визуализация маршрутов и анимация полёта.
- Экспорт KML/GeoJSON.

### 1.2 Ограничения хакатона (это и есть нефункциональные требования)
- **Команда:** 4–5 человек, узкая специализация неизбежна → архитектура должна допускать параллельную работу с минимальными точками синхронизации.
- **Время:** от нескольких дней до недели, с промежуточной сдачей (концепция/архитектура/прототип/алгоритм) и финальной (код, демо, документация).
- **Среда исполнения:** современный браузер на ПК, жюри само запускает решение → должно подниматься одной командой (`docker compose up`), без ручной настройки окружения.
- **Оценка:** обоснованность подхода, качество алгоритма, масштабируемость, качество демо. Не оценивается: production-надёжность, безопасность, многопользовательский доступ. Это значит — не тратить время на auth, миграции, CI/CD дальше базового, HA.
- **Главный риск** — не алгоритмический, а интеграционный: части, сделанные параллельно, не сходятся вовремя. Архитектура ниже спроектирована так, чтобы этот риск снять.

## 2. Высокоуровневая архитектура

```
┌─────────────────────────┐        REST / WS         ┌──────────────────────────┐
│   Web UI (React + TS)   │ ───────────────────────▶ │   API (FastAPI)          │
│  Leaflet: карта, ввод    │ ◀─────────────────────── │  - CRUD сценариев        │
│  сценария, экспорт,      │   прогресс job'а по WS   │  - запуск планирования   │
│  Гант, Парето-график     │                           │  - экспорт KML/GeoJSON   │
└─────────────────────────┘                           └────────────┬─────────────┘
                                                                     │ вызывает как
                                                                     │ библиотеку
                                                        ┌────────────▼─────────────┐
                                                        │   core (чистый Python,    │
                                                        │   без веб-зависимостей)   │
                                                        │                           │
                                                        │  geometry/  — проекции,   │
                                                        │    NFZ, visibility graph  │
                                                        │  coverage/  — галсы,      │
                                                        │    декомпозиция полигона  │
                                                        │  cost/      — время,      │
                                                        │    энергия, ветер         │
                                                        │  allocator/ — VRP-эвристика│
                                                        │    + локальный поиск      │
                                                        │  export/    — KML/GeoJSON │
                                                        └────────────┬─────────────┘
                                                                     │
                                                        ┌────────────▼─────────────┐
                                                        │  Storage: файлы/SQLite   │
                                                        │  (сценарии, планы, логи  │
                                                        │  прогонов для бенчмарка) │
                                                        └───────────────────────────┘
```

**Принцип №1, самый важный:** `core` — это отдельный Python-пакет с собственным CLI (`python -m core.plan scenario.json -o mission.geojson`) и без единой строчки, знающей про FastAPI. Он тестируется и бенчмаркается сам по себе. Если фронт или API не успеют — у вас всё равно есть работающее и демонстрируемое ядро. Это единственная гарантия против «склеили в последнюю ночь и не собралось».

### 2.1 Структура репозитория (монорепо)

```
geoscan/
  core/                # ядро, см. выше — чистый Python-пакет
    geometry.py
    coverage.py
    cost_model.py
    allocator.py
    export.py
    cli.py
    tests/
  api/                 # тонкий слой FastAPI поверх core
    main.py
    jobs.py            # асинхронный запуск планирования + WS-прогресс
    schemas.py         # pydantic-модели = контракт с фронтом
  web/                 # React + TS + Leaflet
  scenarios/           # тестовые сценарии для демо и бенчмарка (JSON)
  docs/                # архитектура, алгоритм, API, user guide, ограничения
  docker-compose.yml
```

## 3. Детальный дизайн

### 3.1 Модель данных (контракт между core / API / фронтом)

Фиксируется в первый час работы — pydantic-модели одновременно служат JSON Schema для фронта.

| Сущность | Ключевые поля |
|---|---|
| `Scenario` | `area` (полигон), `no_fly_zones[]`, `airspace_boundary`, `depots[]`, `reserve_sites[]`, `survey_type`, `sensor_params`, `wind` |
| `Vehicle` | `id`, `type` (fixed-wing/copter), `cruise_speed`, `max_wind`, `endurance`, `payload_compatibility[]`, `turn_radius` (для самолётного типа) |
| `Sortie` | `vehicle_id`, `depot_id`, `waypoints[]`, `altitude`, `speed_profile`, `phase` (взлёт/галс/разворот/посадка), `duration`, `battery_reserve` |
| `Mission` | `sorties[]`, `objective` (`alpha`), `metrics` (makespan, total_flight_time), `status` |
| `Job` | `id`, `scenario_id`, `state`, `progress`, `partial_mission` — для стриминга промежуточных решений по WS |

### 3.2 API-контракт (минимальный, стабильный)

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/scenarios` | создать/загрузить сценарий |
| `POST` | `/scenarios/{id}/plan?alpha=0.5` | запустить оптимизацию → `job_id` |
| `WS` | `/ws/jobs/{job_id}` | прогресс + промежуточные планы |
| `GET` | `/jobs/{job_id}` | статус/результат (фолбэк, если WS недоступен) |
| `GET` | `/missions/{id}/export?format=kml\|geojson\|plan\|waypoints` | экспорт |
| `POST` | `/benchmark` | прогон core на наборе сценариев → таблица метрик (для «масштабируемости» в критериях оценки) |

### 3.3 Асинхронность и прогресс
Оптимизация может идти секунды–минуты. Celery/Redis — избыточная инфраструктура для хакатона. Достаточно `asyncio.create_task` + in-memory `dict[job_id, JobState]` в самом API-процессе, и WebSocket, который push'ит `progress` и промежуточный `partial_mission` каждые N итераций локального поиска. Анимация «решение улучшается на глазах» — дешёвый и сильный демо-эффект, закладывайте его в интерфейс `allocator` с самого начала (callback `on_improvement(mission)`), а не приклеивайте потом.

### 3.4 Frontend — основные экраны
1. **Редактор сценария** — рисование полигона/NFZ, расстановка depots, выбор типа съёмки, состав флота, ветер.
2. **Запуск и мониторинг** — слайдер `alpha` (makespan ↔ налёт), прогресс-бар, live-обновление карты.
3. **Результат** — маршруты на карте, анимация по времени, диаграмма Ганта по бортам, таблица метрик vs baseline, кнопки экспорта.
4. **Бенчмарк (опционально, если останется время)** — график время-решения / качество на разных масштабах области и флота — прямое попадание в критерий «масштабируемость».

### 3.5 Хранилище
SQLite/файлы по умолчанию. PostGIS — опционально, добавляется только если понадобятся пространственные запросы поверх множества сценариев; не блокирует MVP. Не тратить время на это в первые дни.

## 4. Ключевые архитектурные решения

| Решение | Выбор | Альтернатива | Почему |
|---|---|---|---|
| Монолит vs микросервисы | Модульный монолит (`core` + тонкий `api`) | Отдельные сервисы geometry/allocator/export | Микросервисы добавляют сетевые вызовы и деплой-сложность без выгоды при команде 4–5 человек и сроке в дни |
| Оптимизатор | Своя эвристика (constructive + 2-opt/or-opt + ALNS) над `core`-моделью стоимости | OR-Tools CP-SAT/Routing «из коробки» | Кастомная стоимость (ветер, многовылетность, разные типы бортов, развороты) плохо ложится на стандартные callback'и OR-Tools; своя эвристика даёт больше контроля и её проще объяснить в презентации. OR-Tools можно держать как fallback/сравнение, если позволит время |
| Прогресс выполнения | WebSocket с промежуточными решениями | Поллинг `GET /jobs/{id}` | WS даёт «живую» анимацию улучшения решения на демо почти бесплатно; поллинг — обязательный fallback на случай проблем с сетью на площадке |
| Хранилище | Файлы/SQLite | PostGIS с самого начала | Экономит первые часы разработки; пространственные запросы для MVP не нужны |
| Граница `core`/веб | Жёсткая — `core` не знает про FastAPI | Логика оптимизации внутри API-хендлеров | Позволяет тестировать/бенчмаркать ядро отдельно и не терять его, если фронт не успевает |
| Проекция координат | Единая метрическая проекция (UTM/локальная) на входе в `core`, WGS84 только на границе с UI и экспортом | Считать в градусах | Расстояния/площади в градусах некорректны географически — источник тихих, незаметных на глаз ошибок |

**Что это усложняет:** нужно с первого часа договориться и заморозить pydantic-схемы — если их менять на ходу, ломаются все три потока параллельно. Назначьте одного человека «владельцем схемы».

**Что стоит пересмотреть, если проект будет жить дальше хакатона:** PostGIS для истории сценариев, очередь задач (Celery/RQ) при реальной многопользовательской нагрузке, деконфликтинг бортов в реальном времени, интеграция с реальными данными воздушного пространства и рельефа.

## 5. Порядок разработки

Ниже — не жёсткая дата-сетка (не знаю фактическую длительность вашего хакатона), а последовательность фаз с внутренними зависимостями. Сжимайте/растягивайте пропорционально.

### Фаза 0 — Фундамент (первые часы)
Делает вся команда вместе, не расходясь по ролям.
- Формализовать модель стоимости и объектную модель на бумаге (это же черновик раздела «алгоритм» в документации).
- Зафиксировать pydantic-схемы `Scenario`/`Vehicle`/`Mission`/`Job` — это контракт, дальше никто их не трогает в одиночку.
- Поднять skeleton: пустой `core` с CLI, пустой FastAPI с одним эндпоинтом, пустой React с Leaflet-картой, `docker-compose.yml`. Закоммитить и убедиться, что у всех поднимается одной командой.
- Подготовить 2–3 тестовых сценария (JSON) — маленький, средний, «злой» (полигон с дырками и NFZ впритык к границе).

### Фаза 1 — Вертикальный срез (следующие ~1/4 времени)
Цель: сквозной путь работает end-to-end, пусть даже наивно.
- `geometry`: проекция, вычитание NFZ, простейшие прямые галсы без учёта ветра и разворотов.
- `allocator`: наивное деление — N равных полос на N бортов (это же ваш **baseline** для будущего сравнения, не выбрасывайте).
- `export`: KML/GeoJSON из плана.
- `api`: `/scenarios`, `/plan` синхронно (без WS пока), `/export`.
- `web`: ввод полигона на карте → отправка → отрисовка полученных маршрутов.
- **Контрольная точка:** к концу фазы кто угодно в команде должен суметь нарисовать полигон в браузере и увидеть на карте реальные (пусть грубые) маршруты, экспортировать KML и открыть его в Google Earth. Если это не работает — не начинайте улучшать алгоритм, пока не заработает.

### Фаза 2 — Углубление (основная часть времени, работает параллельно)
- **Геометрия:** направление галсов с учётом ветра, обрезка по NFZ и границам, visibility graph для транзитных перелётов, радиус разворота для самолётного типа.
- **Модель стоимости:** время по фазам полёта (взлёт/крейсер/разворот/посадка), ветровой снос, энергетический резерв, достижимость резервной площадки.
- **Оптимизатор:** переход от наивного деления к multi-trip VRP-эвристике (constructive + локальный поиск), критерий `alpha·makespan + (1-alpha)·total_time`.
- **API/инфраструктура:** асинхронный job runner, WebSocket-прогресс, `on_improvement`-callback из allocator.
- **Frontend:** слайдер критерия, анимация полёта, Гант, live-обновление через WS, таблица метрик vs baseline.
- Параллельно, с самого начала фазы — вести `docs/` (архитектура уже есть — этот документ, алгоритм, известные ограничения растут по ходу дела, не в последнюю ночь).

**К моменту промежуточной сдачи** у вас уже должны быть готовы: этот документ (концепция + архитектура), кликабельный прототип интерфейса из Фазы 1, и текстовое описание алгоритма из модели стоимости выше — то есть промежуточная сдача закрывается почти как побочный продукт Фаз 0–1, если документацию писать по ходу.

### Фаза 3 — Интеграция и данные для оценки
- Сборка бенчмарк-набора (несколько масштабов области/флота) и прогон core-CLI на нём → график время/качество и таблица «наш алгоритм vs baseline» — прямое закрытие критериев «масштабируемость» и «эффективность маршрутов».
- Пересечение с воздушным пространством и деконфликтинг между бортами — минимум как проверка постфактум с явным предупреждением на карте, если ресурсы ограничены.
- Экспорт в `.plan`/`.waypoints` как бонус, если время позволяет (сильный аргумент на вопросах жюри про применимость).

### Фаза 4 — Заморозка и демо (последние часы)
- Feature freeze — никаких новых фич, только фиксы.
- Прогнать демо-сценарий целиком минимум три раза подряд без перезапуска окружения.
- Записать видео демо как бэкап на случай сбоя сети/докера на площадке.
- Добить `docs/`: архитектура, алгоритм, инструкция запуска (`docker compose up` и всё), API (если есть), user guide, честный список известных ограничений.

### Распределение по ролям (ориентир на 4–5 человек)
| Роль | Основная зона | Взаимодействует с |
|---|---|---|
| Геометрия/GIS | `core/geometry.py`, `core/coverage.py` | Владелец схемы, Оптимизатор |
| Оптимизатор | `core/cost_model.py`, `core/allocator.py`, бенчмарк | Геометрия, API (callback прогресса) |
| Backend/интеграция | `api/`, `core/export.py`, Docker, WS | Все |
| Frontend | `web/` | API (контракт), Оптимизатор (что показывать в анимации) |
| Документация/демо (с середины фазы 2) | `docs/`, сценарий демо, презентация | Все |

## 6. Риски и порядок урезания scope, если не успеваете

Если время поджимает — режьте функциональность в этом порядке (снизу — то, что режется в последнюю очередь, потому что прямо в критериях оценки):
1. Экспорт в `.plan`/`.waypoints` (оставить только KML/GeoJSON).
2. Учёт рельефа/ЦМР — задекларировать как ограничение.
3. Деконфликтинг бортов в воздухе — задекларировать как ограничение.
4. Анимация и Гант на фронте — оставить статичную визуализацию маршрутов.
5. **Не резать:** сравнение с baseline и переключение критерия оптимизации — это то, что визуально и содержательно доказывает «интеллектуальность» сервиса и прямо соответствует критериям оценки.
