## 1. Вводные

### 1.1 Функциональные требования

Из ТЗ, уточнённые заказчиком:

- **Вход:** область съёмки — мультиполигон с отверстиями (№9); тип съёмки и требуемый GSD (№26); флот БВС; площадки взлёта-посадки и резервные; запретные зоны с высотами и окнами времени (№40); граница разрешённого пространства; **слой высотных препятствий** (№2); **коридор высот** (№10); ветер (№45). Геометрия приходит **файлами** — ввод на карте не нужен (№8).
- **Расчёт:** высота съёмки AGL из GSD; шаг галсов из перекрытия (№24, №25); **разделение области между бортами** (№27, №46); маршруты с обходом зон и препятствий; **расписание** всех вылетов (№31); разведение бортов (№4, №37).
- **Оптимизация:** минимум срока или минимум ресурса техники при необязательном дедлайне (№23).
- **Выход:** полный план или отчёт о невыполнимости с рекомендациями (№42). KML/GeoJSON в WGS84 + расписание + **документ формата** (№21).
- **Интерфейс:** REST API с OpenAPI — основной (№11, №20); веб — визуализация маршрутов, результатов оптимизации, выбор критерия, выгрузка (ТЗ, раздел 4).

### 1.2 Нефункциональные требования

- **Команда:** 3–5 человек, узкая специализация неизбежна → архитектура допускает параллельную работу с минимумом точек синхронизации.
- **Время:** несколько дней, с промежуточной сдачей (концепция, архитектура, прототип интерфейса, алгоритм) и финальной (код, демо, презентация, документация, инструкция).
- **Запуск:** `docker compose up` на машине жюри без ручных шагов (№17). Интернет есть (№16).
- **Масштаб:** ~100 км², до 10 бортов, типично до 10–15 (№2, №43).
- **Время расчёта:** ориентир 30 минут, качество важнее скорости (№3).
- **Не нужно:** авторизация, роли, восстановление после сбоя (№15), офлайн (№16).

### 1.3 Как проверяют решение

Это определяет архитектуру сильнее, чем всё остальное (№4, №5, №7):

1. **Краш-тест** — нет столкновений и опасных сближений, нет залёта в запретные зоны, нет опасных пролётов у высотных препятствий.
2. **Разумность решений** и число учтённых аспектов предметной области.
3. **Законченность и сбалансированность**: работающий сквозной путь важнее глубины одной части.
4. Оценщики — бизнес, разработчики, специалисты по БАС. Решение должно быть понятно всем трём.

Следствие: безопасность плана — не «проверка в конце, если успеем», а свойство, которое обеспечивается на трёх уровнях (§3.4) и независимо перепроверяется. **Главный риск проекта** — не алгоритмический и не интеграционный, а **выданный план с нарушением жёсткого правила**. Второй по величине — интеграционный: части, сделанные параллельно, не сходятся вовремя.

### 3.1 Конвейер

| Стадия | Вход → выход | Что делает | Эпик |
|---|---|---|---|
| Приём | файлы → `Scenario` | Разбор JSON и геослоёв, валидация (самопересечения, пределы значений), WGS84 → метры | E1, E9 |
| Съёмка | `Scenario` → `SurveyPlan` | Для каждого борта: высота AGL из GSD, ширина захвата, шаг галсов, путевая скорость | E2 |

| Распределение | подобласти → `Allocation` | Подобласти по вылетам бортов, площадки взлёта и посадки, режим оптимизации | E6 |
| Покрытие | подобласть × борт → галсы | Галсы со своим шагом, направление с учётом ветра, порядок захода | E3 |
| Полёт | вылет → фазы | Время по фазам, энергия, выполнимость по ветру | E4, E5 |
| Расписание | вылеты → `Schedule` | Время старта, эшелоны, разведение, ожидание | E14 |
| Проверка | план → нарушения | Независимый краш-тест жёстких правил | E7 |
| Итог | всё → `Mission` | Выполним: план. Невыполним: причины и рекомендации | E15 |
| Выгрузка | `Mission` → файлы | KML, GeoJSON, расписание, WGS84 | E8 |

Распределение и покрытие связаны обратной связью: чтобы оценить вылет, распределению нужна длительность съёмки подобласти конкретным бортом. Покрытие вызывается из распределения как функция стоимости и кешируется по паре «подобласть × борт». Стадия остаётся чистой.

### 3.3 Алгоритм

Черновик пояснительной записки: общее описание и минимальное обоснование (№6).

**1. Параметры съёмки.** Высота над поверхностью, дающая требуемый GSD: `H = GSD · N / (2 · tan(θ/2))`, где `N` — число пикселей кадра поперёк полёта, `θ` — угол поля зрения в той же плоскости (эквивалентно `H = GSD · f / p` через фокусное расстояние и размер пикселя). Ширина захвата `W = GSD · N`, шаг галсов `d = W · (1 − s)`, где `s` — поперечное перекрытие из конфига типа съёмки (≥ 0,5, №25). Путевая скорость ограничена интервалом съёмки: `V ≤ GSD · N_вдоль · (1 − f_прод) / t_мин`. Высота ограничена сверху коридором, потолком борта и облачностью.

**2. Декомпозиция.** Рабочая маска режется на компактные подобласти; размер — порядка того, что борт снимает за вылет. Кандидаты метода — полосы вдоль выбранного направления с нарезкой на ячейки, либо трапецеидальная (boustrophedon) декомпозиция с последующим слиянием; выбор — в E3. Соседние подобласти перекрываются не меньше чем на поперечное перекрытие.

**3. Распределение.** Задача — маршрутизация нескольких транспортных средств с несколькими депо, многовылетностью и разнотипным флотом (multi-depot, multi-trip, heterogeneous VRP) над подобластями. Ограничение вылета — полётное время не больше 80% автономности (отсечка 20%, №34). Стоимость подобласти для борта — время её съёмки этим бортом (покрытие, §3.1). Решение в три шага: baseline (равные полосы по числу бортов) → жадная конструктивная эвристика со вставкой по наибольшему сожалению → локальный поиск (перенос и обмен подобластей между вылетами, 2-opt внутри вылета). Критерии — бриф §4.3.

*Сделано на 2026-09-27 (шаг 2, `core/allocate/greedy.py`).* Делится время, а не площадь. Площадки: не приписанные сценарием борта расставляются по одному, коптеры раньше самолётов, туда, где осталось больше досягаемой работы, не забранной уже стоящими бортами. Очередь: вылет получает борт, который раньше освободится (минимум срока), либо самый производительный, пока укладывается в дедлайн (минимум ресурса). Вылет: затравка — самая дальняя посильная подобласть, добор — ближайшие к последней; «сожаление» — в порядке выбора: борт сначала берёт подобласти, которые не может снять ни один борт с меньшей дальностью. Время вылета — та же модель полёта, что в плане; нижняя граница по прямой отсекает безнадёжных кандидатов до точной сборки. Шаг 3 (локальный поиск) не начат. Сравнение с baseline — `python -m core.cli compare`.

**4. Направление галсов.** Перебор угла с шагом в несколько градусов; стоимость — число разворотов, суммарная длина и штраф за угол между галсом и ветром. Галсы вдоль ветра дают меньший угол сноса и более ровную съёмку (№45).

**5. Выполнимость по ветру.** На галсе с путевой скоростью `V` вдоль единичного направления `ê` и векторе ветра `w` (куда дует; из метеоконвенции переводится только в `core/flight/wind.py`) воздушная скорость `v_a = V·ê − w`. Галс выполним, если `|v_a|` не выше максимальной воздушной скорости борта, а для самолёта — и не ниже минимальной. Плюс паспортный предел ветра. Время съёмки от ветра не зависит: путевую скорость держит автопилот (№45).

**6. Расписание и разведение** (§3.4). Вылеты ставятся на ось времени по очереди (list scheduling); каждый новый вылет проверяется на конфликт с уже поставленными в пространстве и времени; конфликт снимается сдвигом старта, ожиданием или сменой эшелона.

### 3.4 Безопасность плана: три уровня разведения + независимая проверка

| Уровень | Как обеспечивается | Эпик |
|---|---|---|
| **В плане** | Подобласти разных бортов не пересекаются; зоны манёвра на концах галсов входят в подобласть при проверке. Самолёты и мультироторы не чередуются на соседних галсах | E3, E6 |
| **По вертикали** | Съёмка — на высоте из GSD. Перелёт — на своём эшелоне внутри коридора высот (№10: «коридор до 700 м, чтобы развести аппараты»). Эшелон отсчитывается от **собственной** высоты съёмки борта и разнесён не меньше вертикального минимума и от чужой съёмки, и от чужих эшелонов: гнать коптер к эшелону самолёта незачем — набор и снижение стоят времени и заряда | E14 |
| **По времени** | Расписание: взлёты и посадки на одной площадке и пересечения перелётов разнесены во времени; при конфликте — задержка старта или ожидание (самолёт — круг, мультиротор — зависание, №37; резервная площадка допустима как зона ожидания, №41) | E14 |
| **Проверка** | Валидатор строит траектории заново из готового плана и проверяет все жёсткие правила, не доверяя стадиям. Минимумы разделения — самолёт ~300 м, мультиротор 50 м (№37). Зона манёвра считается занятой всё время съёмки своей подобласти и сравнивается с зонами других вылетов: разворот в траектории — отрезок, а петля может лечь где угодно внутри зоны (№38) | E7 |

Запретные зоны, граница пространства и высотные препятствия обходятся на этапе перелётов (E5) и отсекаются маской на этапе декомпозиции (E1, E3). Препятствие выше высоты съёмки минус запас становится горизонтальным запретом для съёмки.

### 3.5 Невыполнимость

Частичных планов нет (инвариант 10). Невыполнимость распознаётся **как можно раньше** и объясняется:

| Где распознаётся | Пример причины | Рекомендация |
|---|---|---|
| Съёмка (E2) | Требуемый GSD недостижим ни одной камерой флота в пределах коридора и потолка | Камера с другим углом или разрешением, выше коридор |
| Полёт (E4) | Ветер выше предела всех бортов на любом направлении галсов | Другая модель, другой день |
| Распределение (E6) | Подобласть дальше радиуса действия всех бортов с одного заряда | Площадка ближе (с предлагаемым местом), модель с большей автономностью |
| Расписание (E14) | Дедлайн не выполним даже при минимуме срока | Ещё борт, снять дедлайн |
| Временные зоны (E14) | Подход к подобласти закрыт временной зоной на весь горизонт | Подождать окончания запрета |

### 3.7 Асинхронность и прогресс

Расчёт может идти минуты (ориентир до 30, №3). Фоновая задача внутри процесса API + поллинг статуса. Celery/Redis — избыточная инфраструктура. WebSocket с промежуточными решениями («план улучшается на глазах») — только если останется время: заказчику важнее разумность и безопасность плана, чем анимация оптимизации.

### 3.8 Frontend — экраны

1. **Сценарий** — загрузка файлов сценария и слоёв, просмотр слоёв на карте, панель параметров: тип съёмки, GSD, флот, ветер, коридор, режим оптимизации, дедлайн. **Рисования нет** (№8, №12).
2. **Расчёт** — выбор режима, запуск, прогресс.
3. **Результат** — маршруты по бортам, подобласти и зоны манёвра; **расписание** диаграммой по бортам (№31); метрики; сравнение с baseline; кнопки выгрузки. При невыполнимости — причина и рекомендации.
4. **Сравнение вариантов** — бонус (№14): два плана рядом, фронт Парето.

### 3.9 Хранилище

Файлы и/или SQLite. Сценарии уже переживают перезапуск; задачи — пока только в памяти. История прогонов и версии планов — бонус (№14) — переносятся на диск. PostGIS не нужен.

### 3.10 Внешние данные

Интернет доступен (№16), ограничений на внешние данные нет (№18). Подложка OSM — онлайн, офлайн-кеш не нужен. ЦМР — через провайдер `core/terrain/` с шагом выборки 20–30 м (№10) и дисковым кешем; стадии в сеть не ходят. Недоступность источника — понятная ошибка.

## 4. Ключевые архитектурные решения

| Решение | Выбор | Альтернатива | Почему |
|---|---|---|---|
| Монолит vs микросервисы | Модульный монолит (`core` + тонкий `api`) | Отдельные сервисы | Сетевые вызовы и сложность деплоя без выгоды при команде 3–5 человек и сроке в дни |
| **Единица распределения** | **Подобласть**; галсы строятся после распределения, у каждого борта свои | Общая сетка галсов на весь флот, галсы раздаются поштучно | Разные камеры — разный шаг (№27); к самолёту не ближе 300 м и зоны разворота на концах галсов (№37, №38) — чередование галсов разных бортов даёт сближения по построению; полигон подобласти — естественная единица выгрузки (№21) |
| Оптимизатор | Своя эвристика: конструктивная + локальный поиск | OR-Tools | Стоимость с зонами манёвра, многовылетностью, разными площадками и разведением плохо ложится на стандартные callback'и; свою эвристику проще объяснить трём аудиториям. OR-Tools заказчик не запрещает — допустим для сравнения |
| **Критерии** | Два режима: минимум срока; минимум ресурса (налёт + циклы) при дедлайне. Свёртка по α — для Парето | Только взвешенная сумма «срок + налёт» | Так сформулировал заказчик (№23); циклы взлёт-посадка изнашивают технику сверх налёта |
| **Невыполнимость** | Полный план или отчёт с причиной и рекомендацией | Частичный план с предупреждениями | Заказчик: «задание либо выполнено полностью, либо невыполнено» (№42) |
| **Безопасность** | Разведение на трёх уровнях + независимый валидатор; нарушение = невыполнимость | Проверка постфактум с предупреждением на карте | Главный способ проверки — краш-тест (№4) |
| **Ветер** | Выполнимость + направление галсов + заход; не входит во время и энергию | Треугольник скоростей во времени и расходе | На галсе автопилот держит путевую скорость; для расхода ветер непредсказуем (№36, №45) |
| **Энергия** | Линейна по полётному времени, отсечка 20% | Пофазные множители мощности | «Линейной модели будет достаточно, лучше иметь запас» (№35) |
| **Разворот самолёта** | Защитная зона манёвра, петля не строится | Точная геометрия петли, схема «через галс» | «Постарайтесь это максимально упростить» (№38) |
| Прогресс | Поллинг | WebSocket | Проще и надёжнее; анимация оптимизации заказчику не критична |
| Хранилище | Файлы / SQLite | PostGIS | Пространственные запросы поверх множества сценариев не нужны |
| Граница `core` / веб | Жёсткая: `core` не знает про FastAPI | Логика в API-хендлерах | Ядро тестируется и показывается отдельно; консоли заказчику достаточно (№11) |
| Проекция | UTM по центру области внутри `core`, WGS84 на входе и выходе | Считать в градусах | Расстояния и площади в градусах неверны, ошибка тихая. Заказчик работает в WGS84 (№10, №21) — это граница системы, а не внутренняя модель |
| **Внешние данные** | Онлайн допустимы через провайдер с кешем | Всё скачивать заранее | Требования офлайна нет (№16) |

**Что это усложняет:** контракт v2 затрагивает почти все стадии. Его надо принять целиком и один раз, до начала E3, E6, E14, иначе параллельные потоки будут ломать друг друга. Назначить одного владельца схемы.

**Что пересмотреть, если проект будет жить дальше хакатона:** очередь задач при многопользовательской нагрузке, приём зон ОРВД напрямую из источника, деконфликтинг в реальном времени по телеметрии, радиовидимость (№29 — сейчас вне объёма).

## 5. Порядок разработки

Фазы 0 и 1 пройдены на прежних допущениях (см. [`current_state.md`](current_state.md)): каркас, контракт v1, сквозной путь «сценарий → расчёт → карта», baseline. Дальше:

### Фаза 1b — Выравнивание по ответам заказчика
Делает вся команда вместе, до расхождения по ролям.
- Принять **контракт v2** (E0) и перегенерировать TS-типы.
- Демо-сценарий в масштабе заказчика: ~100 км², до 10 бортов, зоны постоянные и временные, препятствия, коридор высот. Заведомо невыполнимый сценарий.
- Снять с конвейера то, что заказчик назвал лишним: ветер из времени и энергии, пофазные множители мощности, выдачу частичных планов.
- Закрыть пробел оптики RGB-камер Геоскан 201 (E2) — без него 100 км² снимать нечем.
- **Контрольная точка:** демо-сценарий проходит конвейер на заглушках и выдаёт либо план, либо отчёт о невыполнимости, но не частичный план.

### Фаза 2 — Углубление (параллельно)
- **Гео:** мультиполигон, препятствия, зоны 3D + время, коридор; ЦМР — после основного.
- **Покрытие:** декомпозиция, галсы по бортам, направление с ветром, зоны манёвра.
- **Полёт и перелёты:** фазы, выполнимость по ветру, обход зон и препятствий.
- **Оптимизатор:** конструктивная эвристика → локальный поиск, два режима.
- **Разведение:** расписание, эшелоны, ожидание.
- **Валидатор:** краш-тест с намеренно испорченными планами в тестах.
- **API и веб:** загрузка слоёв, расписание, отчёт о невыполнимости.
- **Документы по ходу:** пояснительная записка из §3.3, документ формата выгрузки.

**К промежуточной сдаче:** этот документ (концепция и архитектура), прототип интерфейса из фазы 1, описание алгоритма из §3.3.

### Фаза 3 — Интеграция и доказательства
- Прогон на наборе сценариев, таблица «наш алгоритм против baseline» в обоих режимах, фронт Парето.
- Бонусы по остатку времени: подбор площадок, история прогонов и сравнение, заход на посадку самолёта, ЦМР.

### Фаза 4 — Заморозка и демо
- Feature freeze — только исправления.
- Демо-сценарий целиком минимум три раза подряд без перезапуска окружения; сценарий с примером препятствий заказчика — тоже.
- Видеозапись демо как бэкап.
- Документация: архитектура, пояснительная записка, инструкция запуска, API (OpenAPI), руководство пользователя, формат выгрузки, известные ограничения.

### Распределение по ролям (ориентир на 3–5 человек)

| Роль | Основная зона | Взаимодействует с |
|---|---|---|
| Геометрия/GIS | `core/geo/`, `core/terrain/`, `core/coverage/`, `core/transit/` | Владелец схемы, Оптимизатор |
| Оптимизатор | `core/allocate/`, `core/deconflict/`, `core/advise/`, бенчмарк | Геометрия, Валидация |
| Полёт и валидация | `core/survey/`, `core/flight/`, `core/validate/` | Все стадии ядра |
| Backend и интеграция | `api/`, `core/export/`, Docker, документ формата | Все |
| Frontend | `web/` | API (контракт) |

## 6. Риски и порядок урезания

| Риск | Вероятность | Что делаем |
|---|---|---|
| Выданный план нарушает жёсткое правило | Высокая без независимого валидатора | Валидатор E7 с тестами на испорченных планах; нарушение = невыполнимость |
| Нет оптики RGB-камер Геоскан 201 → 100 км² RGB снимать нечем | Высокая | Вывод пикселей из мегапикселей и углов (E2); параллельно — запрос заказчику |
| Контракт v2 принимается по частям и ломает потоки | Средняя | Принять одним изменением в фазе 1b |
| Разведение 10 бортов не сходится | Средняя | Подобласти разнесены в плане, эшелоны по вертикали — большая часть конфликтов снимается построением, расписанию остаются взлёты, посадки и перелёты |
| ЦМР медленная или недоступна | Средняя | Опциональна; без неё высоты AGL, рельеф плоский, ограничение объявлено |

Если время поджимает — режьте в таком порядке:
1. Формат наземной станции `.plan` / `.waypoints`.
2. Подбор площадок, заход на посадку самолёта, окна светлого времени.
3. Анимация полёта и инспектор стадий.
4. ЦМР — объявить ограничение.
5. График времени расчёта.

**Не резать:** безопасность плана (E5, E7, E14), полноту или явную невыполнимость, переключение критерия и сравнение с baseline, расписание, документ формата выгрузки. Это то, что заказчик проверяет в первую очередь и что прямо названо в его ответах.
