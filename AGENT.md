# AGENT.md — инструкции для агентной разработки

Документ адресован агенту (и человеку), который пишет код в этом репозитории.
Источник истины по архитектуре — [`PROJECT_BRIEF.md`](PROJECT_BRIEF.md). Этот файл — операционные правила поверх него.

Порядок чтения перед началом работы:
1. [`docs/current_state.md`](docs/current_state.md) — что уже сделано, что заглушка (**обязательно, всегда**)
2. [`PROJECT_BRIEF.md`](PROJECT_BRIEF.md) — архитектура, ограничения, инварианты
3. [`docs/epics.md`](docs/epics.md) — граница твоего эпика
4. [`docs/architecture.md`](docs/architecture.md) — обоснования решений (более ранний документ, см. §9 «Расхождения»)

## 1. Контекст и архитектурный инвариант

Сервис планирования и распределения беспилотных авиационных работ: по сценарию (область съёмки, тип съёмки, флот БВС, площадки взлёта, запретные зоны, границы воздушного пространства, ветер) рассчитываются индивидуальные полётные задания для группы разнотипных БВС и выгружаются в KML/GeoJSON. Оптимизация — по двум критериям: makespan и суммарный налёт.

Архитектура — **модульный монолит с конвейером чистых стадий**:

```
Scenario ──▶ SurveyPlan ──▶ CoverageSet ──▶ Allocation ──▶ Mission ──▶ Files
            (параметры     (галсы,         (вылеты по     (план +      (KML,
             съёмки)        обрезанные      бортам)        warnings)    GeoJSON)
                            по маске)
```

Каждая стадия: типизированный вход → типизированный выход, **без состояния**, знает о соседях только через типы из `core/schemas.py`.

Границы слоёв:

```
web/    React + TS + Vite + Leaflet   ──REST+поллинг──▶  api/
api/    FastAPI, тонкий слой          ──импорт──────▶    core/
core/   чистый Python, НОЛЬ веб-зависимостей, собственный CLI
```

**Жёсткое правило:** `core` не импортирует ничего из `api` и `web`. Ядро запускается как `python -m core.cli` и живёт без веба. Это страховка на случай, если веб-слой отстанет.

Направление зависимостей строго одностороннее: `web → api → core`. Обратных стрелок нет ни одной.

## 2. Карта репозитория

| Путь | Ответственность | Эпик |
|---|---|---|
| `core/schemas.py` | **Общий контракт.** pydantic-модели: `Scenario`, `Vehicle`, `SurveyPlan`, `Strip`, `Leg`, `Sortie`, `Mission` | E0 |
| `core/assumptions.py` | **Все физические константы и допущения**, каждая с комментарием об источнике | E0 |
| `core/geo/` | Проекции WGS84 ↔ метрическая, рабочая маска области, буферы, валидация геометрии | E1 |
| `core/survey/` | Сенсорная модель, GSD, высота, ширина захвата, шаг галсов, пресеты типов съёмки, совместимость «борт × нагрузка» | E2 |
| `core/coverage/` | Декомпозиция области, генерация галсов, выбор направления, развороты | E3 |
| `core/flight/` | Ветер, кинематика, время и энергия по фазам полёта, выполнимость вылета | E4 |
| `core/transit/` | Граф видимости, обход запретных зон, кратчайшие перелёты | E5 |
| `core/allocate/` | Распределение по флоту: baseline → конструктивная эвристика → локальный поиск | E6 |
| `core/validate/` | Проверка готового плана, список предупреждений | E7 |
| `core/export/` | KML / GeoJSON | E8 |
| `core/cli.py` | Прогон конвейера и бенчмарк без веба | E0, E12 |
| `api/` | FastAPI: сценарии, запуск конвейера фоновой задачей, статус, промежуточные стадии, отдача файлов | E9 |
| `web/` | React + TS + Leaflet: редактор сценария, инспектор стадий, визуализация | E10, E11 |
| `data/vehicles.yaml` | ТТХ БВС из официальных источников, с указанием источника на каждый параметр | E0 |
| `scenarios/` | Тестовые сценарии: простой / средний / «злой» (дырки, NFZ впритык к границе) | E0 |
| `docs/` | Документация, `current_state.md` — живой | E13 |

### Куда класть новый код

- Новая физика полёта → `core/flight/`, константы → `core/assumptions.py`.
- Новый тип съёмки → пресет в `core/survey/`, не в `coverage` и не в API.
- Новая метрика плана → вычисляется в `core/`, API только отдаёт готовое.

### Куда код класть **нельзя** (типичные ошибки)

- ❌ **Геометрические и физические расчёты в слое `api/`.** Это самая частая ошибка. API — транспорт: валидация запроса, вызов `core`, сериализация ответа. Если в хендлере появились `shapely`, `pyproj`, `numpy` или арифметика с координатами — расчёт написан не там.
- ❌ **Логика в компонентах `web/`.** Фронтенд рисует то, что вернул API, и не пересчитывает маршруты, длины и время самостоятельно.
- ❌ **Импорт `api` или `web` из `core`** — любой, включая «только для типов».
- ❌ **Дублирование схем.** Типы фронтенда генерируются из `core/schemas.py`, не пишутся руками.
- ❌ **Константы по месту использования** вместо `core/assumptions.py`.

## 3. Чек-лист инвариантов (проверять перед завершением работы)

Раздел 5 брифа в виде проверяемого списка. Код, нарушающий любой пункт, считается сломанным **независимо от того, проходят ли тесты**.

- [ ] **1. Вся геометрия — в метрической проекции.** WGS84 живёт только на границах системы: на входе из сценария и на выходе в экспорт. В `core` между границами — метры. Расчёты в градусах дают неверные расстояния и площади, и ошибка тихая.
- [ ] **2. `core` не знает про веб.** Ни одного импорта из `api`. Проверка: `python -m core.cli` отрабатывает при полностью отсутствующем `api/`.
- [ ] **3. `core/schemas.py` не изменён** — или изменён осознанно, с явной отметкой в `docs/current_state.md` и перегенерацией TypeScript-типов (см. §4).
- [ ] **4. Направление ветра — метеорологическая конвенция (откуда дует).** Перепутанный знак даёт зеркальный план, обнаруживается только на демонстрации.
- [ ] **5. Ни одного магического числа** вне `core/assumptions.py`. Каждая константа там — с комментарием об источнике.
- [ ] **6. Ни одной выдуманной ТТХ БВС.** Только `data/vehicles.yaml` из официальных источников. Неизвестная характеристика помечается как пробел, а не заполняется правдоподобным числом.
- [ ] **7. Время полёта не считается как «длина / скорость».** Учтены фазы полёта, ветер, развороты, резерв заряда.
- [ ] **8. Baseline-алгоритм на месте.** Равномерное деление области не удалено, не «отрефакторено в ноль», доступно для сравнения.

## 4. Правила работы с контрактом

`core/schemas.py` — единственная точка синхронизации между тремя параллельными потоками работы. Её правка ломает всех одновременно.

Порядок изменения схемы:

1. Убедиться, что изменение действительно необходимо, а не обходной путь вокруг чужой незавершённой работы.
2. Внести правку **аддитивно**, если возможно: новое опциональное поле со значением по умолчанию не ломает соседей, переименование поля — ломает.
3. Перегенерировать JSON Schema и TypeScript-типы для фронтенда (см. команду в [`CLAUDE.md`](CLAUDE.md)).
4. Записать в `docs/current_state.md` → «Журнал изменений» **отдельной строкой с пометкой о правке контракта**: что изменилось, зачем, что может сломаться у соседей.
5. Прогнать тесты и CLI на всех сценариях из `scenarios/`.

Ломающее изменение схемы без отметки в `current_state.md` — дефект сам по себе, даже если код корректен.

## 5. Параллельная агентная работа

**Одна сессия — один эпик — одна ветка.** Ветка именуется по эпику: `e3-coverage`, `e6-allocate`.

- **Не трогай модули за пределами своего эпика.** Карта в §2 задаёт границы. Нужна правка в чужой зоне — опиши её в отчёте и в `current_state.md`, но не делай.
- **Нужен ещё не реализованный модуль — пиши заглушку**, а не блокируйся и не переписывай чужую зону.
  - Заглушка возвращает правдоподобные данные корректного типа из `core/schemas.py`.
  - Помечается явным `TODO(E<номер эпика>): заглушка, заменить на реальную реализацию`.
  - Заносится в раздел «Заглушки и временные решения» в `current_state.md` с указанием, какой эпик её закроет.
  - Заглушка **не должна молча выглядеть как настоящий расчёт**: логируй предупреждение или проставляй флаг в результате.
- **Конфликт границ** (два эпика правят один файл) — не разрешается «на месте»: фиксируй в `current_state.md` и оставляй решение команде.
- Коммить только свою зону. Побочные правки чужих файлов — в отдельный коммит с объяснением.

## 6. Обязательные шаги перед завершением задачи

Ни один из пунктов не пропускается, даже если изменение кажется тривиальным.

1. **Тесты** — `pytest` проходит полностью. Новый код стадии сопровождается тестами.
2. **Линтер и форматтер** — прогнаны, замечаний нет.
3. **CLI на тестовых сценариях** — `python -m core.cli` отрабатывает на **всех** сценариях из `scenarios/`, включая «злой». Не только на удобном.
4. **Чек-лист инвариантов из §3** — пройден по пунктам.
5. **`docs/current_state.md` обновлён** — статус эпика, что работает, что заглушка, новые допущения, журнал изменений.
6. **Отчёт о работе** в формате §8.

## 7. Что запрещено делать самостоятельно

Требует явной задачи или решения команды:

- ❌ **Выдумывать технические характеристики БВС.** Источник — `data/vehicles.yaml` и официальные страницы производителя. Нет данных — это пробел, фиксируемый в `current_state.md`, а не правдоподобное число.
- ❌ **Добавлять зависимости вне раздела 3 брифа.** Разрешено: NumPy, Shapely, pyproj, FastAPI, pydantic v2, uvicorn, React 18, TypeScript, Vite, Leaflet, pytest, опционально rasterio. Запрещено: сервисы Google, Celery/Redis/RabbitMQ, обязательный PostGIS, тяжёлые CSS-фреймворки и UI-киты, библиотеки с несвободными или вирусными лицензиями (только MIT / BSD / Apache 2.0 и совместимые).
- ❌ **Вводить обращения к внешним API в рантайме.** На площадке демонстрации может не быть интернета. Тайлы, рельеф и любые внешние данные скачиваются заранее и лежат в репозитории или томе. См. [`docs/external_sources.md`](docs/external_sources.md).
- ❌ **Менять целевую функцию оптимизации.** `α·makespan + (1−α)·суммарный налёт` — фиксирована. Изменение весов, добавление слагаемых, смена нормировки — только по явной задаче.
- ❌ **Удалять или отключать baseline-алгоритм.** Он всегда даёт результат и служит точкой сравнения, доказывающей эффективность решения.
- ❌ **Подключать OR-Tools как основу оптимизатора.** Допустим только как опциональная альтернатива для сравнения с собственной эвристикой.
- ❌ **Заменять поллинг на WebSocket** без отдельного решения — см. §9.
- ❌ **Вводить авторизацию, роли, многопользовательский режим, миграции БД** — вне объёма проекта.

## 8. Требования к коду

**Типизация.** Все публичные функции стадий аннотированы. Границы стадий — только типы из `core/schemas.py`, не голые `dict` и не кортежи.

**Докстринги с единицами измерения.** У каждой публичной функции стадии — докстринг, явно называющий единицы: метры, секунды, радианы, м/с, Вт·ч, доля (0..1). Отсутствие единиц в докстринге функции, принимающей число, — дефект: именно на смешении градусов с радианами и км с метрами ломаются такие расчёты.

```python
def leg_duration(length_m: float, ground_speed_mps: float) -> float:
    """Длительность участка.

    Args:
        length_m: длина участка, метры (метрическая проекция).
        ground_speed_mps: путевая скорость, м/с (с учётом ветра).

    Returns:
        Длительность, секунды.
    """
```

**Детерминированность.** Любой недетерминированный алгоритм (локальный поиск, ALNS, перебор с рандомизацией) принимает `seed` и по умолчанию воспроизводим. Один и тот же сценарий с одним seed даёт побитово один и тот же план. Без этого невозможен бенчмарк и невозможна отладка на демонстрации.

**Никаких магических чисел** вне `core/assumptions.py`. Число в формуле расчёта, не являющееся математической константой самого выражения, — в `assumptions.py` с комментарием об источнике. Этот файл механически превращается в раздел «известные ограничения» документации, который требуется по ТЗ.

**Чистота стадий.** Стадия не пишет в глобальное состояние, не ходит в сеть, не читает файлы вне переданных ей путей, не зависит от порядка вызова.

**Понятные ошибки.** Невыполнимый сценарий — это `warning` или типизированное исключение с объяснением, а не тихий пустой результат и не падение по `IndexError`.

## 9. Расхождения между документами

`PROJECT_BRIEF.md` — источник истины. `docs/architecture.md` написан раньше и в нескольких местах отражает более раннее решение. Где расходятся — следовать брифу:

| Вопрос | `architecture.md` (раннее) | **`PROJECT_BRIEF.md` (актуально)** |
|---|---|---|
| Прогресс расчёта | WebSocket + поллинг как фолбэк | **Поллинг.** WS — «под вопросом», только если останется время после функциональности, дающей баллы |
| Контракт данных | `api/schemas.py` | **`core/schemas.py`** |
| CLI | `python -m core.plan` | **`python -m core.cli`** |
| Модули ядра | `geometry.py`, `cost_model.py`, `allocator.py` | **пакеты `geo/`, `survey/`, `coverage/`, `flight/`, `transit/`, `allocate/`, `validate/`, `export/`** |

Обнаружил новое расхождение — не решай его молча: зафиксируй в `docs/current_state.md` → «Известные проблемы и долги».

## 10. Формат отчёта о работе

Каждая завершённая сессия заканчивается отчётом такой структуры (он же — основа записи в `docs/current_state.md`):

```markdown
## Эпик E<N> — <название>, ветка <branch>

### Что сделано
- <конкретно, по модулям; что теперь работает end-to-end, а что — на заглушках>

### Принятые допущения
- <допущение> — <почему; перенесено в assumptions.py / ждёт ответа организаторов>

### Что осталось незакрытым
- <пункт> — <почему: не в объёме эпика / блокирует другой эпик / не хватило данных>

### Новые обнаруженные пробелы
- <неизвестная ТТХ, расхождение в документах, неоднозначность в ТЗ, чужая зона, требующая правки>

### Контракт
- core/schemas.py: не изменён / изменён — <что именно и что может сломаться>

### Проверки
- pytest: <результат>
- линтер/форматтер: <результат>
- CLI на scenarios/: <результат по каждому сценарию, включая «злой»>
- чек-лист инвариантов §3: <пройден / расхождения>
```

Отчёт честный: «почти готово» — не статус. Если сквозной путь не работает, так и пишется.
