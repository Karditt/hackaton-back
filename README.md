# GEOSCAN — планирование и распределение беспилотных авиационных работ

Сервис принимает описание задания — область съёмки (полигон или мультиполигон),
тип съёмки и требуемое разрешение, флот БВС, площадки взлёта-посадки,
запретные зоны с высотами и окнами действия, высотные препятствия, коридор
высот, ветер — и **делит работу между разнотипными бортами**: рассчитывает
полётное задание каждого вылета и общее расписание, выгружает их в KML,
GeoJSON и CSV.

Итог всегда один из двух: **полный план**, прошедший краш-тест (нет
сближений бортов, залёта в запретные зоны, пролётов у препятствий), или
**отчёт о невыполнимости** — с причиной и тем, чего не хватает: площадки,
борта, другой модели. Частичных планов нет.

Оптимизация — два режима: минимум срока выполнения работ и минимум ресурса
техники (налёт плюс циклы взлёт-посадка).

> **Состояние: каркас, приведённый к ответам заказчика.** Конвейер собран
> целиком и проходит на всех сценариях, включая демо в масштабе заказчика
> (~95 км², 10 бортов). Распределение — пока baseline, декомпозиция и
> расписание — простые заглушки; они объявляют себя в каждом плане (поле
> `stub_stages`). Подробно и честно — [`docs/current_state.md`](docs/current_state.md).
> Требования заказчика — [`docs/customer_qa.md`](docs/customer_qa.md).

## Запуск

### Всё сразу, на чистой машине

```bash
docker compose up
```

Интерфейс — <http://localhost:5173>, API и его описание OpenAPI —
<http://localhost:8000/docs>. Тестовые сценарии подгружаются автоматически.
Геометрия на карте не рисуется: исходные данные готовятся в ГИС и приходят
файлами (так решил заказчик).

В интерфейсе правятся параметры задания: тип съёмки и GSD, состав флота,
ветер, коридор высот, начало работ, дедлайн, межвылетная подготовка. Правки
считаются копией сценария (`<сценарий>--custom`), исходный файл не меняется.

### Только ядро, без веба

Ядро — самостоятельный Python-пакет без веб-зависимостей. Оно считает и
выгружает планы, даже если каталоги `api/` и `web/` удалить целиком.

```bash
pip install -e ".[dev]"
python -m core.cli scenarios/demo_100km2.json -o out/
```

В каталог `out/` пишется комплект: `<сценарий>.geojson`, `.kml` и
`.schedule.csv` на весь план и `<сценарий>.<борт>.kml` — индивидуальное
полётное задание каждого борта: вылеты, ключевые точки, трек для шкалы
времени Google Earth, расписание. Задание одного борта в файл:

```bash
python -m core.cli scenarios/simple.json -o out/gemini1.kml --board geoscan-gemini_1
```

Режим оптимизации переключается ключом `--mode min_makespan|min_resource`.
Что лежит в файлах и как их читать без нашего кода —
[`docs/export_format.md`](docs/export_format.md).

Прогон на всех тестовых сценариях сразу:

```bash
python -m core.cli --batch scenarios/ -o out/
```

Реестр допущений — то, из чего вырастает раздел «известные ограничения».
«!» — допущение команды, «*» — значение заказчика:

```bash
python -m core.cli assumptions
```

Промежуточные стадии конвейера одним файлом (для отладки и инспектора стадий):

```bash
python -m core.cli scenarios/nasty.json -o out/ --dump-stages out/
```

### Тесты и линтер

```bash
pytest
ruff check core api tests
ruff format core api tests
```

### Типы для фронтенда

Типы TypeScript порождаются из контракта и руками не пишутся. После **любой**
правки `core/schemas.py`:

```bash
python -m core.cli export-schema -o web/src/types/schema.json
cd web && npm run gen:types
```

## Как это устроено

Конвейер чистых стадий: каждая принимает типизированный вход, возвращает
типизированный выход и знает о соседях только через типы из `core/schemas.py`.

```
Scenario → SurveyPlan → Decomposition → Allocation → Coverage
         → вылеты → Schedule → Validation → Mission → Files
```

1. **Съёмка** — по требуемому GSD, углу поля зрения и разрешению камеры считается
   высота над поверхностью; шаг галсов — из перекрытия (конфиг по типам съёмки);
   путевая скорость — такая, чтобы борт удержал её при заданном ветре.
2. **Декомпозиция** — область делится на подобласти, размер которых укладывается
   в вылет самого «малоёмкого» борта.
3. **Распределение** — подобласти по вылетам бортов (сейчас baseline: равные площади).
4. **Покрытие** — каждый борт строит галсы в своих подобластях со своим шагом;
   у самолёта на концах галсов — защитная зона манёвра.
5. **Вылеты** — фазы полёта, эшелон перелёта в коридоре высот, обход запретных
   зон и препятствий по графу видимости.
6. **Расписание** — вылеты на общей оси времени; старт сдвигается, пока есть
   сближения бортов или вылет попадает во временную зону в её окно.
7. **Краш-тест** — независимая проверка готового плана по жёстким правилам.
   Нарушение — невыполнимость, а не предупреждение.

```
web/    React + TypeScript + Vite + Leaflet   ──REST + поллинг──▶  api/
api/    FastAPI, тонкий слой (OpenAPI)        ──импорт─────────▶   core/
core/   чистый Python, ноль веб-зависимостей, собственный CLI
```

| Каталог | Что внутри |
|---|---|
| `core/schemas.py` | Общий контракт: сценарий, стадии, план, расписание, отчёт о невыполнимости |
| `core/assumptions.py` | Все константы и допущения, каждое с источником |
| `core/geo/` | Проекции, мультиполигон, проверка геометрии, зоны с высотами и временем, препятствия, маска съёмки |
| `core/survey/` | GSD → высота, шаг галсов, перекрытия по типам съёмки, путевые скорости при ветре |
| `core/coverage/` | Декомпозиция на подобласти, галсы, зоны манёвра |
| `core/flight/` | Фазы полёта, время, линейный расход заряда, 4D-траектория |
| `core/transit/` | Обход запретных зон и препятствий: граф видимости |
| `core/allocate/` | Распределение по бортам, критерии двух режимов, baseline |
| `core/deconflict/` | Эшелоны перелёта, расписание, разведение бортов |
| `core/validate/` | Краш-тест готового плана |
| `core/advise/` | Причины невыполнимости и рекомендации |
| `core/export/` | GeoJSON, KML, расписание CSV; обзор плана и задание каждого борта |
| `api/` | FastAPI: сценарии с проверкой на приёме, фоновый расчёт, поллинг, выгрузка |
| `web/` | Панель параметров, карта маршрутов со слоями и фильтром по борту, метрики, расписание, отчёт о невыполнимости, выгрузка |
| `data/vehicles.yaml` | ТТХ БВС из официальных документов, с источником у каждого параметра |
| `data/survey_presets.yaml` | Перекрытия по типам съёмки |
| `scenarios/` | Тестовые и демо-сценарии |

## Тестовые сценарии

| Сценарий | Что проверяет | Ожидаемый итог |
|---|---|---|
| `simple.json` | Сквозной путь целиком: два коптера с одной площадки | Выполним |
| `medium.json` | Область с отверстием, две запретные зоны, самолёт и коптеры | Выполним: зоны обходятся, самолёт не берёт подобласти, где ему негде развернуться |
| `demo_100km2.json` | Масштаб заказчика: ~95 км², мультиполигон, 10 бортов, постоянная, низковысотная и временная зоны, препятствия, коридор 700 м | Выполним; Геоскан 801 исключён — для площадной RGB-съёмки он не подходит |
| `nasty.json` | Два отверстия, зона впритык к границе, обрезка пространством, ветер у предела, предел числа вылетов | **Невыполним**: не хватает вылетов — причина и рекомендация названы |

Прогонять нужно все. Сценарий, который всегда зелёный, ничего не проверяет.

## Правила, которые нельзя нарушать

1. **Вся геометрия — в метрической проекции.** WGS84 живёт только на границах:
   вход сценария и выход экспорта. Ошибка от расчётов в градусах — тихая.
2. **`core` не знает про веб.** Ни одного импорта из `api`.
3. **`core/schemas.py` — общий контракт.** Правка ломает три потока работы
   сразу, поэтому только осознанно и с отметкой в `current_state.md`.
4. **Ветер — метеорологическая конвенция** (откуда дует). Он определяет
   выполнимость и направление галсов, во время и расход не входит.
5. **Физические константы — только в `core/assumptions.py`.** ТТХ БВС — только
   из `data/vehicles.yaml`, не выдумываются.
6. **Baseline никогда не удаляется** — это точка сравнения, которой измеряется
   эффективность оптимизатора.
7. **Ни один выданный план не нарушает жёстких правил безопасности.**
8. **Частичных планов нет.**

Полный чек-лист и правила разработки — [`AGENT.md`](AGENT.md).

## Лицензии и источники данных

Картографическая подложка — OpenStreetMap, лицензия ODbL, атрибуция
«© OpenStreetMap contributors» выводится на карте. Технические
характеристики БВС взяты из официальных документов производителя, лежащих в
`docs/`, страниц продуктов geoscan.ru (через веб-архив) и паспортов камер Sony;
источник указан у каждого параметра в `data/vehicles.yaml`. В каталоге —
Геоскан 201, 201 Термо, Lite, 401 Геодезия, 801 и Gemini.
