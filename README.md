# GEOSCAN — планирование и распределение беспилотных авиационных работ

Сервис принимает описание задания — область съёмки (полигон или мультиполигон),
тип съёмки и требуемое разрешение, флот БВС, площадки взлёта-посадки,
запретные зоны с высотами и окнами действия, высотные препятствия, коридор
высот, ветер — и **делит работу между разнотипными бортами**: рассчитывает
полётное задание каждого вылета и общее расписание, выгружает их в KML,
GeoJSON и CSV.

Итог всегда один из двух: **полный план**, прошедший краш-тест (нет
сближений бортов, залёта в запретные зоны, пролётов у препятствий), или
**отчёт о невыполнимости** — с причиной и тем, чего не хватает: площадки,
борта, другой модели. Частичных планов нет.

Оптимизация — два режима: минимум срока выполнения работ и минимум ресурса
техники (налёт плюс циклы взлёт-посадка). Флот задания — пул доступной техники:
какие борта пойдут в работу, решает расчёт, и план называет свой состав.

> **Состояние (2026-09-29).** Конвейер собран целиком и проходит на всех
> сценариях, включая демо в масштабе заказчика (~95 км², 10 бортов) и два
> сценария на его данных по 245 км². Нарезка — по островкам, направление галсов —
> с учётом ветра; распределение — конструктивная эвристика под несколько целевых
> сроков с локальным поиском, обе видят расписание (baseline оставлен для
> сравнения, `python -m core.cli compare`); варианты распределения считаются в
> нескольких процессах; расписание — задержка на земле с 4D-разведением, по
> желанию — только при Солнце не ниже порога. В вебе, кроме плана: подсказка
> «сколько бортов к сроку», фронт «срок — ресурс», подбор места ещё одной
> площадки, сравнение с равномерным делением — каждый ответ подтверждён полным
> планом с краш-тестом. Свой сценарий — из слоёв KML любой ГИС; площадок нет —
> места подбирает сервис. Вся документация — [`docs/`](docs/README.md).

## Запуск

### Всё сразу, на чистой машине

```bash
docker compose up
```

Интерфейс — <http://localhost:5173>, API и его описание OpenAPI —
<http://localhost:8000/docs>. Тестовые сценарии подгружаются автоматически.
Геометрия на карте не рисуется: исходные данные готовятся в ГИС и приходят
файлами (так решил заказчик).

В интерфейсе правятся параметры задания: тип съёмки и GSD, состав флота,
ветер, коридор высот, начало работ, дедлайн, межвылетная подготовка. Правки
считаются копией сценария (`<сценарий>--custom`, в списке — с пометкой
«изменённые параметры»), исходный файл не меняется.

Три вкладки: **«План и карта»** — сценарий, параметры, расчёт, карта с
менеджером исходных данных (область, зоны, препятствия, площадки — показ
каждого вида включается отдельно) и высотой обзора в углу; **«Расписание»** —
диаграмма по бортам и таблицы во всю ширину; **«Техника»** — парк бортов с
отметкой «в строю», модели с ТТХ и полезная нагрузка. ТТХ любой модели
каталога можно поправить, модель — скрыть, можно завести свою; правки
уходят в расчёт вместе со сценарием, а к исходному каталогу можно вернуться
по полю, по модели или целиком. Флот расчёта набирается из бортов парка,
которые в строю; парк и правки хранятся на сервере. Свой сценарий — кнопка
«Новый сценарий из своих файлов»: слои KML (область, зоны, препятствия,
площадки) и параметры JSON собираются ядром с отчётом импорта; площадок нет —
места подбирает сервис, параметров нет — берутся у выбранного сценария и
правятся в панели. Кнопки «Загрузить» в менеджере данных заменяют один слой
выбранного сценария (копией). Границу между панелью и картой можно двигать.
Подробно — [`docs/user_guide.md`](docs/user_guide.md).

### Только ядро, без веба

Ядро — самостоятельный Python-пакет без веб-зависимостей. Оно считает и
выгружает планы, даже если каталоги `api/` и `web/` удалить целиком.

```bash
pip install -e ".[dev]"
python -m core.cli scenarios/demo_100km2.json -o out/
```

В каталог `out/` пишется комплект: `<сценарий>.geojson`, `.kml` и
`.schedule.csv` на весь план и `<сценарий>.<борт>.kml` — индивидуальное
полётное задание каждого борта: вылеты, ключевые точки, трек для шкалы
времени Google Earth, расписание. Задание одного борта в файл:

```bash
python -m core.cli scenarios/simple.json -o out/gemini1.kml --board geoscan-gemini_1
```

Режим оптимизации переключается ключом `--mode min_makespan|min_resource`.
Что лежит в файлах и как их читать без нашего кода —
[`docs/export_format.md`](docs/export_format.md).

Прогон на всех тестовых сценариях сразу:

```bash
python -m core.cli --batch scenarios/ -o out/
```

Подсказки по пулу техники: флот сценария — пул, из которого берутся N самых
производительных бортов, и для каждого N считается настоящий план.

```bash
python -m core.cli hints scenarios/demo_100km2.json --boards 4       # срок при 4 бортах
python -m core.cli hints scenarios/demo_100km2.json --deadline-h 6   # сколько бортов к сроку 6 ч
python -m core.cli hints scenarios/demo_100km2.json --sweep          # срок при каждом N
```

То же в API: `POST /scenarios/{id}/hints?boards=4` (или `deadline_s=…`,
`sweep=true`), поллинг `GET /hints/{id}`; план из ответа — обычная задача
`plan_job_id` со всеми выгрузками.

Реестр допущений — то, из чего вырастает раздел «известные ограничения».
«!» — допущение команды, «*» — значение заказчика. Вторая команда обновляет
раздел реестра в [`docs/known_limitations.md`](docs/known_limitations.md)
(тест следит, чтобы он не отставал):

```bash
python -m core.cli assumptions
python -m core.cli assumptions --update docs/known_limitations.md
```

Промежуточные стадии конвейера одним файлом (для отладки и инспектора стадий):

```bash
python -m core.cli scenarios/nasty.json -o out/ --dump-stages out/
```

### Тесты и линтер

### Типы для фронтенда

Типы TypeScript порождаются из контракта и руками не пишутся. После **любой**
правки `core/schemas.py`:

```bash
python -m core.cli export-schema -o web/src/types/schema.json
cd web && npm run gen:types
```

## Как это устроено

Конвейер чистых стадий: каждая принимает типизированный вход, возвращает
типизированный выход и знает о соседях только через типы из `core/schemas.py`.

```
Scenario → SurveyPlan → Decomposition → Allocation → Coverage
         → вылеты → Schedule → Validation → Mission → Files
```

1. **Съёмка** — по требуемому GSD, углу поля зрения и разрешению камеры считается
   высота над поверхностью; шаг галсов — из перекрытия (конфиг по типам съёмки);
   путевая скорость — такая, чтобы борт удержал её при заданном ветре.
2. **Декомпозиция** — подобласть — островок области; крупные режутся на части,
   посильные вылету самого «малоёмкого» борта, у запретных зон для самолёта
   отрезается полоса.
3. **Распределение** — подобласти по вылетам бортов: борт, который раньше
   освободится, берёт самую дальнюю посильную подобласть и добирает ближайшие;
   борта без площадки расставляются туда, где их работа. Вылет сразу ставится в
   расписание: если разведение сдвигает старт, собирается другой. Потом
   локальный поиск доводит план — разгружает вылет, который кончается последним,
   оставляет лишний борт на земле, сливает короткие вылеты, — и каждый ход
   проверяет настоящим расписанием. Baseline (равные площади) — для сравнения:
   `python -m core.cli compare`.
4. **Покрытие** — каждый борт строит галсы в своих подобластях со своим шагом и
   направлением; у самолёта на концах галсов — защитная зона манёвра со стороной
   разворота.
5. **Вылеты** — фазы полёта, эшелон перелёта в коридоре высот, обход запретных
   зон и препятствий по графу видимости.
6. **Расписание** — вылеты на общей оси времени; старт сдвигается, пока есть
   сближения бортов или вылет попадает во временную зону в её окно.
7. **Краш-тест** — независимая проверка готового плана по жёстким правилам.
   Нарушение — невыполнимость, а не предупреждение.

```
web/    React + TypeScript + Vite + Leaflet   ──REST + поллинг──▶  api/
api/    FastAPI, тонкий слой (OpenAPI)        ──импорт─────────▶   core/
core/   чистый Python, ноль веб-зависимостей, собственный CLI
```

| Каталог | Что внутри |
|---|---|
| `core/schemas.py` | Общий контракт: сценарий, стадии, план, расписание, отчёт о невыполнимости |
| `core/assumptions.py` | Все константы и допущения, каждое с источником |
| `core/geo/` | Проекции, мультиполигон, проверка геометрии, зоны с высотами и временем, препятствия, маска съёмки |
| `core/survey/` | GSD → высота, шаг галсов, перекрытия по типам съёмки, путевые скорости при ветре |
| `core/coverage/` | Декомпозиция на подобласти, галсы, зоны манёвра |
| `core/flight/` | Фазы полёта, время, линейный расход заряда, 4D-траектория |
| `core/transit/` | Обход запретных зон и препятствий: граф видимости |
| `core/allocate/` | Распределение по бортам: конструктивная эвристика, локальный поиск, baseline, критерии двух режимов |
| `core/deconflict/` | Эшелоны перелёта, расписание, разведение бортов |
| `core/validate/` | Краш-тест готового плана |
| `core/advise/` | Причины невыполнимости и рекомендации |
| `core/export/` | GeoJSON, KML, расписание CSV; обзор плана и задание каждого борта |
| `core/hints.py` | Подсказки по пулу: срок при N бортах, сколько бортов к сроку — прогонами конвейера |
| `core/pareto.py`, `core/sites.py` | Фронт «срок — ресурс» и подбор места ещё одной площадки — каждый вариант полным расчётом |
| `core/text.py` | Подписи для человека: режимы, типы съёмки, фазы, борта и вылеты, числа по-русски |
| `api/` | FastAPI: сценарии с проверкой на приёме, фоновый расчёт, поллинг, выгрузка |
| `web/` | Вкладки «План и карта», «Расписание», «Техника»: панель параметров, карта с менеджером исходных данных, слоями, легендой и фильтром по борту, итог и сравнение с равномерным делением, подсказка по флоту, фронт «срок — ресурс», подбор площадки, история расчётов, диаграмма расписания, парк бортов и ТТХ, отчёт о невыполнимости, выгрузка |
| `data/vehicles.yaml` | ТТХ БВС из официальных документов, с источником у каждого параметра |
| `data/survey_presets.yaml` | Перекрытия по типам съёмки |
| `scenarios/` | Тестовые и демо-сценарии; `scenarios/sources/` — их исходники в формате заказчика (слои KML и параметры JSON), `scenarios/real/` — сценарий на данных заказчика |

## Тестовые сценарии

| Сценарий (в интерфейсе) | Что проверяет | Ожидаемый итог |
|---|---|---|
| `simple.json` («Простой прямоугольник») | Сквозной путь целиком: два коптера с одной площадки | Выполним |
| `medium.json` («Г-образная область») | Область с отверстием, две запретные зоны, самолёт и коптеры | Выполним: зоны обходятся, самолёт не берёт подобласти, где ему негде развернуться даже с галсами вдоль границы |
| `demo_100km2.json` («Демонстрационный») | Масштаб заказчика: ~95 км², мультиполигон, 10 бортов, постоянная, низковысотная и временная зоны, препятствия, коридор 700 м | Выполним; Геоскан 801 исключён — для площадной RGB-съёмки он не подходит |
| `nasty.json` («Невыполнимый») | Два отверстия, зона впритык к границе, обрезка пространством, ветер у предела, предел числа вылетов | **Невыполним**: не хватает вылетов — причина и рекомендация, проверенная пересчётом |

Прогонять нужно все. Сценарий, который всегда зелёный, ничего не проверяет.

Каждый сценарий хранится и в том виде, в каком данные отдаёт заказчик: три слоя KML — область, зоны ограничений (высоты и окна действия в предложенном формате, `docs/input_formats.md` §3.2), высотные препятствия — и параметры задания JSON, в `scenarios/sources/<сценарий>/`. Кроме четырёх тестовых там описан `real_msk` — сценарий на файлах заказчика из `data/samples/`: 549 участков, 547 препятствий, расчёт около 5 минут, **выполним**. Узкие полосы у круглых зон ограничений самолёт снять не может — разворот задел бы зону, — а коптеру с двух исходных площадок до них не долететь; третья площадка «Восток» с одним Gemini поставлена там, где её рекомендовала сама система.

`real_nw` — **отложенный** сценарий того же рода: на нём алгоритм не настраивают, на нём показывают итог. Зоны и препятствия — настоящие файлы заказчика (к северо-западу от Москвы их больше: 16 зон, 297 препятствий), островки — его же, но разложенные по новому месту группами соседних со случайным поворотом (`python -m core.cli relayout-area`, зерно 1), другие площадки, флот, GSD и ветер; четвёртая площадка — по рекомендации системы, как у `real_msk`. Совпадение JSON сценария с его файлами проверяет `python -m core.cli check-sources` и тест.

## Правила, которые нельзя нарушать

1. **Вся геометрия — в метрической проекции.** WGS84 живёт только на границах:
   вход сценария и выход экспорта. Ошибка от расчётов в градусах — тихая.
2. **`core` не знает про веб.** Ни одного импорта из `api`.
3. **`core/schemas.py` — общий контракт.** Правка ломает три потока работы
   сразу, поэтому только осознанно, аддитивно и с перегенерацией типов фронтенда.
4. **Ветер — метеорологическая конвенция** (откуда дует). Он определяет
   выполнимость и направление галсов, во время и расход не входит.
5. **Физические константы — только в `core/assumptions.py`.** ТТХ БВС — из
   `data/vehicles.yaml` или заданные пользователем в сценарии (помечены
   `user_fields`, план об этом предупреждает); команда их не выдумывает.
6. **Baseline никогда не удаляется** — это точка сравнения, которой измеряется
   эффективность оптимизатора.
7. **Ни один выданный план не нарушает жёстких правил безопасности.**
8. **Частичных планов нет.**

## Лицензии и источники данных

Картографическая подложка — OpenStreetMap, лицензия ODbL, атрибуция
«© OpenStreetMap contributors» выводится на карте. Технические
характеристики БВС взяты из официальных документов производителя, лежащих в
`docs/sources/`, страниц продуктов geoscan.ru (через веб-архив) и паспортов камер Sony;
источник указан у каждого параметра в `data/vehicles.yaml`. В каталоге —
Геоскан 201, 201 Термо, Lite, 401 Геодезия, 801 и Gemini.
