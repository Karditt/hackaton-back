## 1. Суть проекта

Сервис планирования и распределения беспилотных авиационных работ. По описанию задания — область съёмки, тип съёмки и требуемое разрешение, флот БВС, площадки взлёта и посадки, запретные зоны, слой высотных препятствий, коридор высот, ветер — сервис **делит работу между несколькими разнотипными бортами** и рассчитывает для каждого индивидуальное полётное задание и общее расписание. Результат выгружается в KML/GeoJSON в WGS84.

Ядро задачи — распределение работ между бортами (заказчик, №46). Покрытие галсами, модель полёта и обход препятствий нужны, чтобы это распределение было выполнимым и безопасным.

**Выход всегда один из двух:**
- **полный план** — область покрыта целиком, ни одно жёсткое правило безопасности не нарушено;
- **отчёт о невыполнимости** — причина и что нужно добавить: площадку, борт, другую модель, подождать окончания временного запрета (заказчик, №33, №42). Частичных планов нет.

Оптимизация — два режима (заказчик, №23): **минимум срока** выполнения всех работ (makespan) и **минимум ресурса техники** (налёт плюс циклы взлёт-посадка) при необязательном ограничении по сроку.

Масштаб (заказчик, №2, №43): область порядка 100 км², до 10 бортов (типично до 10–15). Время расчёта — ориентир 30 минут; качество плана важнее скорости (№3).

**Как оценивают** (заказчик, №4, №5, №7). Проверяют в основном краш-тестом: нет столкновений и опасных сближений бортов, нет залёта в запретные зоны, нет опасных пролётов у высотных препятствий. В первую очередь смотрят на разумность принятых решений и на то, сколько аспектов предметной области учтено. Важно, чтобы решение было доведено до конца и сбалансировано. Оценивает смешанная группа: бизнес, разработчики, специалисты по БАС. Не оценивается: авторизация, многопользовательский режим, восстановление после сбоя (№15).

**Интерфейс** (заказчик, №8, №11, №12). Основной интерфейс — программный: REST API с OpenAPI и CLI. Веб нужен для визуализации маршрутов, расписания и результатов оптимизации, выбора критерия и выгрузки (ТЗ, раздел 4). **Ввод и редактирование геометрии на карте не делаются**: исходные данные готовятся в ГИС и приходят файлами.

## 2. Архитектурный паттерн

**Модульный монолит с конвейером (pipeline) чистых стадий.**

Система — последовательность стадий-преобразователей. Каждая стадия принимает типизированный вход, возвращает типизированный выход, не хранит состояние и знает о соседях только через типы.

```
Scenario ─▶ SurveyPlan ─▶ Decomposition ─▶ Allocation ─▶ Coverage ─▶ Schedule ─▶ Validation ─▶ Mission ─▶ Files
(WGS84,    (высота,      (подобласти,     (подобласти   (галсы по   (время,     (краш-тест    (план или   (KML,
 файлы)     шаг галсов    зоны манёвра)    по вылетам)   бортам,     эшелоны,    по жёстким    отчёт о     GeoJSON,
            по бортам)                                   ветер)      разведение) правилам)     невыполн.)  расписание)
```

Изменение порядка относительно первой редакции: область сначала **делится на подобласти**, подобласти распределяются по вылетам, и только потом каждый борт строит галсы в своей подобласти со своим шагом и направлением. Раньше строилась одна сетка галсов на весь флот по самому узкому шагу, и галсы раздавались бортам поштучно. Почему сменили:

- разные камеры дают разный шаг галсов — общая сетка заставляет всех снимать с избыточным перекрытием (заказчик, №27);
- самолёту на концах галсов нужна зона разворота, а к самолёту нельзя приближаться ближе ~300 м (№37, №38). Чередующиеся галсы разных бортов в одной сетке дают сближения по построению; компактная подобласть на борт разводит борта в плане естественным образом;
- полигон подобласти — естественная единица выгрузки, если направление галсов борт определяет сам (№21).

Почему модульный монолит, а не микросервисы: сетевые границы между стадиями не дают ничего, кроме сложности деплоя, при команде из трёх человек и сроке в несколько дней. Модульность обеспечивается границами модулей внутри процесса, а не HTTP.

Почему конвейер: отладка по стадиям (видно, где именно сломался план), параллельная работа без взаимных блокировок, возможность показать любую промежуточную стадию на карте во время защиты.

### Слои

```
web/    React + TypeScript + Vite + Leaflet
  │     загрузка файлов сценария, запуск расчёта, карта маршрутов,
  │     расписание, метрики, сравнение вариантов. Рисования на карте нет
  │     REST + поллинг долгих расчётов
api/    FastAPI, тонкий слой — ОСНОВНОЙ интерфейс сервиса (OpenAPI):
  │     сценарии и слои файлами, запуск конвейера, статус, результат, экспорт, история
  │     вызывает core как обычную библиотеку
core/   чистый Python, НОЛЬ веб-зависимостей, собственный CLI
        geo        — проекции, мультиполигон, валидация, маска, препятствия, зоны с высотами и временем
        terrain    — ЦМР: провайдер высот рельефа с шагом выборки и кешем (опционально)
        survey     — GSD → высота AGL, ширина захвата, шаг галсов, перекрытия по типам съёмки
        coverage   — декомпозиция на подобласти, галсы, направление с учётом ветра, зоны манёвра
        flight     — фазы, время, линейная энергия, выполнимость по ветру
        transit    — перелёты в обход запретных зон и препятствий
        allocate   — распределение подобластей по вылетам, два критерия, baseline
        deconflict — расписание, эшелоны перелётов, разведение бортов, ожидание
        validate   — независимый краш-тест плана
        advise     — диагностика невыполнимости, рекомендации, подбор площадок
        export     — KML / GeoJSON / расписание
        cli        — прогон и бенчмарк без веба
        assumptions.py — все физические допущения в одном месте
storage файлы / SQLite: сценарии, планы, история прогонов
```

**Жёсткое правило:** `core` не импортирует ничего из `api` и `web`. Ядро запускается через CLI и живёт без веба. Это страховка на случай, если веб-слой отстанет.

### Упаковка

Docker: два образа (api, web), `docker compose up` поднимает всё одной командой на чистой машине без ручных шагов. Жюри запускает решение само.

## 3. Ограничения по стеку

Вынесено отдельным разделом намеренно: это рамки, за которые не выходим без явного обсуждения командой.

**Заказчик ограничений не ставит** (№18): любые библиотеки, предобученные модели, внешние данные, облачные API и коммерческие компоненты допустимы. Всё, что перечислено ниже, — **решения команды**, а не условия задания. Меняются обсуждением команды, без обращения к заказчику.

### Предпочтительный стек

| Слой | Технологии |
|---|---|
| Ядро | Python 3.11+, NumPy, Shapely (GEOS), pyproj, PyYAML |
| Бэкенд | FastAPI, pydantic v2, uvicorn |
| Фронтенд | React 18, TypeScript, Vite, Leaflet |
| Хранилище | Файлы (JSON) и/или SQLite |
| Упаковка | Docker, docker compose |
| Тесты | pytest, httpx |
| Рельеф (опционально) | rasterio, GeoTIFF, тайлы высот |

Новая зависимость добавляется с отметкой в `docs/current_state.md` и одной строкой обоснования.

### Не используем — решения команды

- **Сервисы, требующие ключа или платной лицензии** (Google Maps, коммерческие SDK). Жюри запускает решение само через `docker compose` — ключей у него нет. Подложка — OpenStreetMap с обязательной атрибуцией «© OpenStreetMap contributors».
- **Celery, Redis, RabbitMQ** — долгие расчёты выполняются фоновой задачей внутри процесса API с поллингом статуса.
- **PostGIS как обязательная зависимость** — в ТЗ он «по желанию», пространственные запросы поверх множества сценариев проекту не нужны.
- **Авторизация, роли, многопользовательский режим, миграции БД** — не в объёме, заказчик подтвердил (№15).
- **Тяжёлые CSS-фреймворки и UI-киты** сверх необходимого.
- **Ввод и редактирование геометрии на карте** — исключены заказчиком (№8, №12).

### Внешние данные в рантайме

Прежний запрет снят: требования работать без интернета нет, доступ к интернету считается имеющимся (№16). Онлайн-источники — подложка, тайлы высот — допустимы при трёх условиях:

1. **Стадии конвейера в сеть не ходят.** Внешние данные получает провайдер (`core/terrain/` для ЦМР) до запуска стадий или через внедрённый интерфейс. Стадия остаётся чистой функцией и тестируется без сети.
2. **Кеш на диске.** Повторный расчёт того же сценария не делает повторных запросов. Запрос к ЦМР медленный — выборка с шагом 20–30 м, а не на каждый метр (№10).
3. **Понятная ошибка.** Недоступность источника — типизированная ошибка с объяснением, а не зависание и не тихий нулевой рельеф.

### Под вопросом, решается отдельно

- OR-Tools — заказчик не запрещает. Как основу оптимизатора не берём: стоимость с зонами манёвра, многовылетностью, разными площадками взлёта и посадки и разведением бортов плохо ложится на стандартные callback'и. Допустим как альтернатива для сравнения.
- WebSocket вместо поллинга — только если останется время после закрытия функциональности, дающей баллы.

## 4. Доменная модель

### 4.1 Типы

| Тип | Суть |
|---|---|
| `Scenario` | Область съёмки (**мультиполигон** с отверстиями), запретные зоны, граница воздушного пространства, **слой высотных препятствий**, **коридор высот**, площадки взлёта-посадки и резервные, тип съёмки и требуемый GSD, ветер, состав флота, режим оптимизации, необязательные время начала работ и дедлайн |
| `NoFlyZone` | Полигон + высотный диапазон + **окно действия** (постоянная зона — без окна). Источник в жизни — ОРВД (№40) |
| `Obstacle` | Высотное препятствие: точка или полигон + высота над землёй. Проходится с буфером по горизонтали или выше по вертикали (№2, №4) |
| `Vehicle` | Тип (самолётный / мультиротор), скорости, автономность, допустимый ветер, радиус разворота, совместимые нагрузки, минимум разделения |
| `SurveyPlan` | По каждому борту: высота съёмки AGL, ширина захвата, шаг галсов, путевая скорость съёмки, перекрытия |
| `Decomposition` | Подобласти (ячейки) с зонами манёвра — единицы распределения |
| `Strip` | Один галс: геометрия, длина, высота, путевая скорость |
| `Leg` | Участок полёта с фазой: взлёт / набор / перелёт / галс / разворот / ожидание / снижение / посадка |
| `Sortie` | Один вылет одного борта: **площадка взлёта и площадка посадки** (могут различаться, №29), подобласти, последовательность `Leg`, эшелон перелёта, время старта, длительность, доля израсходованного заряда |
| `Schedule` | Расписание: вылеты всех бортов на общей оси времени, межвылетная подготовка, ожидания |
| `Mission` | Статус **выполним / невыполним**. Выполним — вылеты, расписание, метрики (makespan, ресурс, налёт, циклы). Невыполним — причины и рекомендации |

Схемы описываются pydantic-моделями в `core/schemas.py` и экспортируются в JSON Schema, из которой генерируются TypeScript-типы для фронтенда.

### 4.2 Правила предметной области

Получены от заказчика. Нарушение любого — ошибка модели, а не допущение.

| Правило | № |
|---|---|
| Качество съёмки задаётся **GSD**. По GSD, углу поля зрения и разрешению матрицы рассчитывается высота съёмки над поверхностью (AGL) | 10, 26 |
| Шаг галсов считается из поперечного перекрытия. Перекрытия задаются конфигом по типу съёмки; минимум для аэрофото-, ИК- и мультиспектральной съёмки — 50% | 24, 25 |
| **Полезная работа — на одной высоте.** Высота меняется только на перелётах, заходе и выходе, в пределах коридора высот | 10 |
| Высоту над поверхностью держит автопилот. Выгружаемая высота — AGL | 10 |
| На галсе автопилот держит **постоянную путевую скорость**. Ветер не меняет время съёмки — он определяет, выполним ли полёт: удержит ли борт путевую скорость в пределах своих воздушных скоростей | 45 |
| Направление ветра учитывается при выборе направления галсов и захода на галс | 45 |
| Расход заряда линеен по полётному времени, ветер в расход не входит. Полёт прекращается при остатке 20% | 34, 35, 36 |
| Не хватает одного заряда на подобласть — план невыполним, а не «долетим потом». Нужен другой борт, другая модель или дополнительная площадка | 33 |
| Одну область можно делить между бортами, в том числе с разными моделями камер одного типа. Стыковка снимков — постобработка, вне задачи | 27 |
| Один борт может выполнять несколько вылетов. Время межвылетной подготовки (замена АКБ, копирование снимков) плохо предсказуемо — параметр сценария | 32 |
| Самолёт не зависает — ожидание выполняется по кругу. К самолёту в круге ожидания не ближе ~300 м, к зависшему мультиротору — не ближе 50 м | 37 |
| На концах галсов самолёту нужна **защитная зона манёвра**, внутри которой он разворачивается как сам считает нужным. Геометрия петли не строится | 37, 38 |
| Запретные зоны бывают постоянные и временные; действуют в своём высотном диапазоне и в своё окно времени | 40 |
| Резервные площадки — только для внештатной посадки и как зона ожидания. Для плановой работы не используются | 41 |
| Старт и посадка одного вылета могут быть на разных площадках. Вместимость площадок не ограничена. Радиовидимость не моделируется | 28, 29 |
| Взлёт с катапульты и парашютная посадка не моделируются | 39 |

### 4.3 Критерии оптимизации

Уточнены заказчиком (№23). Заменяют прежнюю формулу «α·makespan + (1−α)·суммарный налёт».

| Обозначение | Смысл |
|---|---|
| `T` — срок | Makespan: от начала работ до посадки последнего борта, секунды |
| `R` — ресурс | Суммарный налёт всех бортов плюс `τ_цикл` × число вылетов, секунды. `τ_цикл` — износ одного цикла взлёт-посадка в секундах налёта, допущение команды в `assumptions.py` |

Режимы:
1. **Минимум срока** — минимизировать `T`; при равном `T` — меньший `R`.
2. **Минимум ресурса** — минимизировать `R` при `T ≤ дедлайн`. Дедлайн необязателен; без него — просто минимум `R`.

Взвешенная свёртка `α·T + (1−α)·R` остаётся инструментом построения фронта Парето и слайдера в интерфейсе (E12). Она не заменяет режимы.

Формула фиксирована: веса, слагаемые и нормировка меняются только по явной задаче.

## 5. Инварианты, которые нельзя нарушать

Эти правила — источник самых дорогих и самых незаметных ошибок в проекте. Любой код, их нарушающий, считается сломанным независимо от того, проходят ли тесты.

1. **Вся геометрия считается в метрической проекции.** Географические координаты (WGS84) живут только на границах системы: на входе из сценария и на выходе в экспорт. Расчёты в градусах дают неверные расстояния и площади, ошибка тихая.
2. **`core` не знает про веб.** Ни одного импорта из `api`. Ядро должно запускаться как `python -m core.cli`.
3. **`core/schemas.py` — общий контракт.** Изменение схемы ломает сразу несколько параллельных потоков работы. Правка только с явной отметкой в `current_state.md`.
4. **Направление ветра задаётся в метеорологической конвенции** — откуда дует. Перепутанный знак даёт зеркальный план: галсы легли бы поперёк ветра вместо вдоль, а проверка выполнимости смотрела бы не на тот галс. Обнаруживается только на демонстрации.
5. **Физические константы живут только в `core/assumptions.py`**, каждая с источником. Магические числа в коде расчётов запрещены. Значения от заказчика помечаются источником «заказчик, №N» и отделяются от допущений команды. Файл механически превращается в раздел «известные ограничения» документации, который требуется по ТЗ.
6. **Технические характеристики БВС не выдумываются.** Они берутся из `data/vehicles.yaml`, заполняемого командой из официальных источников. Если характеристики неизвестны — это помечается как пробел, а не заполняется правдоподобным числом. Вывод по явной формуле из документированных чисел допустим и помечается как производное поле.
7. **Время вылета не считается как «длина маршрута делить на одну скорость».** Оно складывается по фазам — взлёт, набор, перелёт, галсы, развороты, ожидание, снижение, посадка — каждая со своей скоростью. На галсе используется путевая скорость, которую держит автопилот. Выполнимость проверяется по отсечке заряда 20%.
8. **Baseline-алгоритм (равномерное деление области) никогда не удаляется.** Он всегда даёт результат и служит точкой сравнения для доказательства эффективности.
9. **Жёсткие правила безопасности не нарушаются ни в одном выданном плане.** Ни один участок траектории, включая зоны манёвра, не пересекает запретную зону в её высотном диапазоне и окне действия, не выходит за разрешённое пространство и коридор высот, не проходит ближе допустимого к высотному препятствию. Ни одна пара бортов не сближается ближе минимума разделения. Нарушение — не предупреждение, а невыполнимость: такой план не выдаётся. Главный способ проверки решения заказчиком — именно краш-тест этих правил (№4).
10. **Задание выполняется целиком или объявляется невыполнимым.** Частичный план не выдаётся. Невыполнимость сопровождается причиной на языке пользователя и тем, чего не хватает: площадки, борта, другой модели, окончания временного запрета (№33, №42).

## 7. Внешние источники

### Данные о технике

Официальные документы с техническими параметрами, ссылки из исходного PDF задания (`5. Геоскан.pdf`, раздел 6 «Ресурсы»):
- Геоскан 201 — борт самолётного типа, катапультный старт, парашютная посадка. Радиуса разворота в выдержке руководства нет — выводится из скорости и крена. https://download.geoscan.ru/site-files/201/Geoscan_201_Manual.pdf
- Геоскан 801 — мультиротор, инспекционный. https://download.geoscan.ru/site-files/801/Geoscan_801.pdf?v2
- Геоскан Gemini — квадрокоптер, время полёта около 40 минут. https://download.geoscan.ru/site-files/gemini/Gemini_Specs_EN_RUS.pdf?v2

Характеристики переносятся в `data/vehicles.yaml` с указанием источника для каждого параметра.

При масштабе ~100 км² основную площадь реалистично снимает только Геоскан 201 (7–22 км² за вылет по документу). Поэтому пробел в оптике его RGB-камер из блокера E2 превратился в главный риск демо-сценария — см. `docs/current_state.md` §4.3.

### Референсное ПО (для понимания форматов и UX)

- Geoscan Planner — https://www.geoscan.ru/ru/software/geoscan_planner
- Mission Planner (ArduPilot) — формат `.waypoints`. https://ardupilot.org/planner/docs/mission-planner-installation.html
- QGroundControl — формат `.plan` (JSON). https://qgroundcontrol.com/

### Картографическая подложка

- OpenStreetMap, тайлы `tile.openstreetmap.org`, лицензия ODbL, обязательная атрибуция.
- Офлайн-кеш тайлов не нужен (заказчик, №16). Политика использования публичного тайл-сервера соблюдается: без массового скачивания.

### Рельеф (опционально)

- Заказчик: «считайте, что рельеф у вас есть» (№10). Есть ЦМР в GeoTIFF и серверы тайлов высот; если публичного не найдём — заказчик даст доступ.
- Кандидаты: SRTM (~30 м), Copernicus GLO-30 (~30 м) в GeoTIFF; публичные тайлы высот. Выбор и проверка — в E1.
- Запрос к ЦМР медленный: выборка с шагом 20–30 м и дисковый кеш.
- В OpenStreetMap данных о рельефе нет, это отдельный источник.

### Высотные препятствия

- Заказчик даст минимальный пример области и слоя препятствий (№44). До его получения используем свой пример в том же духе: GeoJSON, точки и полигоны с высотой.

### Спецификации форматов

- GeoJSON — RFC 7946
- KML — спецификация OGC; критично корректно выставить режим высоты (`clampToGround` / `relativeToGround` / `absolute` дают три разных смысла). Высоты проекта — над поверхностью, режим `relativeToGround`.
- Формат выгрузки проекта описывается отдельным документом — требование заказчика (№21).

### Вопросы к организаторам

Три исходных вопроса брифа закрыты ответами заказчика 2026-09-18: площадки задаёт пользователь, подбор сервисом — бонус; многовылетность — да; эталонных сценариев нет, формат выгрузки — на наше усмотрение с обязательным описанием; ветер — для выполнимости и направления галсов; рельеф — считать доступным; специфика самолёта — круг ожидания и зоны манёвра, без катапульты и парашюта.

## 8. Что нужно сгенерировать на основе этого брифа

### 8.1 `AGENT.md` — инструкции для агентной разработки

Документ адресован агенту, который пишет код в этом репозитории. Должен содержать:

- **Контекст и архитектурный инвариант** — конвейер стадий, границы слоёв, правило «core не знает про веб».
- **Карту репозитория** — какой модуль за что отвечает, куда класть новый код, куда точно не класть (геометрические расчёты в слое API — типичная ошибка).
- **Инварианты из раздела 5** этого брифа в виде явного чек-листа, который агент проверяет перед завершением работы.
- **Правила работы с контрактом** — `core/schemas.py` менять только осознанно, с отметкой в `current_state.md`; при изменении схемы перегенерировать TypeScript-типы.
- **Правила для параллельной агентной работы:** одна сессия — один эпик — одна ветка; не трогать модули за пределами эпика; если для работы нужен ещё не реализованный модуль — писать заглушку с правдоподобными данными и явным `TODO`, а не блокироваться и не переписывать чужую зону.
- **Обязательные шаги перед завершением задачи:** прогон тестов, прогон линтера/форматтера, прогон CLI на тестовых сценариях из `scenarios/`, обновление `docs/current_state.md`.
- **Что запрещено делать самостоятельно:** выдумывать технические характеристики БВС, добавлять зависимости вне раздела ограничений по стеку, вводить внешние API-вызовы в рантайме, менять целевую функцию оптимизации без явной задачи, удалять baseline-алгоритм.
- **Требования к коду:** типизация, докстринги для публичных функций стадий с указанием единиц измерения (метры, секунды, радианы), детерминированность (фиксированные seed'ы), отсутствие магических чисел вне `assumptions.py`.
- **Формат отчёта о работе:** что сделано, какие допущения приняты, что осталось незакрытым, какие новые пробелы обнаружены.

### 8.2 `CLAUDE.md` — рабочий контекст

Короткий файл в корне, который читается автоматически в начале сессии. Не дублирует `AGENT.md`, а указывает на него и даёт оперативное:

- Одно-два предложения о проекте.
- Ссылки: `AGENT.md`, `PROJECT_BRIEF.md`, `docs/architecture.md`, `docs/epics.md`, `docs/current_state.md`.
- Команды: установка, запуск через docker compose, прогон тестов, прогон CLI на тестовом сценарии, генерация TypeScript-типов.
- Три-пять самых критичных инвариантов одной строкой каждый.
- Правило: начинать сессию с чтения `docs/current_state.md`, заканчивать его обновлением.

### 8.3 `docs/current_state.md` — текущее состояние проекта

Живой документ, обновляемый в конце каждой сессии. Структура:

- **Статус по эпикам** — таблица: эпик, состояние (не начат / в работе / готов), что конкретно работает, что заглушка.
- **Что работает end-to-end прямо сейчас** — честное описание сквозного пути, без «почти готово».
- **Заглушки и временные решения** — список с указанием, какой эпик их закроет.
- **Принятые допущения** — те, что ещё не перенесены в `assumptions.py`, и те, что ждут ответа организаторов.
- **Известные проблемы и долги.**
- **Журнал изменений** — дата, что изменилось, особо отмечать правки контракта `core/schemas.py`.

Первая версия файла создаётся сразу и описывает состояние «репозиторий создан, код не написан» — чтобы документ существовал с первого дня и обновлялся, а не создавался задним числом.
