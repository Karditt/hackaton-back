# GEOSCAN — бриф проекта

Исходный документ для генерации `CLAUDE.md`, `AGENT.md` и `docs/current_state.md`.
Кладётся в корень репозитория как `PROJECT_BRIEF.md` и остаётся источником истины по архитектуре.

---

## 1. Суть проекта

Сервис планирования и распределения беспилотных авиационных работ. Веб-приложение, которое по описанию задания (область съёмки, тип съёмки, флот БВС, площадки взлёта, запретные зоны, границы воздушного пространства, ветер) рассчитывает индивидуальные полётные задания для группы разнотипных беспилотников и выгружает их в KML/GeoJSON.

Оптимизация поддерживает минимум два критерия: минимизация времени выполнения работ (makespan) и минимизация суммарного налёта.

Контекст: хакатон. Решение оценивается по обоснованности подхода, качеству алгоритмов, эффективности построенных маршрутов, масштабируемости и качеству демонстрации. Не оценивается: production-надёжность, безопасность, многопользовательский режим.

## 2. Архитектурный паттерн

**Модульный монолит с конвейером (pipeline) чистых стадий.**

Система — последовательность стадий-преобразователей. Каждая стадия принимает типизированный вход, возвращает типизированный выход, не хранит состояние и знает о соседях только через типы.

```
Scenario ──▶ SurveyPlan ──▶ CoverageSet ──▶ Allocation ──▶ Mission ──▶ Files
            (параметры     (галсы,         (вылеты по     (план +      (KML,
             съёмки)        обрезанные      бортам)        warnings)    GeoJSON)
                            по маске)
```

Почему модульный монолит, а не микросервисы: сетевые границы между стадиями не дают ничего, кроме сложности деплоя, при команде из трёх человек и сроке в несколько дней. Модульность обеспечивается границами модулей внутри процесса, а не HTTP.

Почему конвейер: отладка по стадиям (видно, где именно сломался план), параллельная работа без взаимных блокировок, возможность показать любую промежуточную стадию на карте во время защиты.

### Слои

```
web/    React + TypeScript + Vite + Leaflet
  │     редактор сценария, инспектор стадий, визуализация результата
  │     REST + поллинг долгих расчётов
api/    FastAPI, тонкий слой: сценарии, запуск конвейера, статус, экспорт
  │     вызывает core как обычную библиотеку
core/   чистый Python, НОЛЬ веб-зависимостей, собственный CLI
        geo       — проекции, рабочая маска области
        survey    — сенсорная модель, GSD, шаг галсов, пресеты типов съёмки
        coverage  — галсы, направление, развороты
        flight    — ветер, время, энергия, выполнимость
        transit   — граф видимости, обход запретных зон
        allocate  — распределение по флоту, критерии оптимальности
        validate  — проверка плана
        export    — KML / GeoJSON
        cli       — прогон и бенчмарк без веба
        assumptions.py — все физические допущения в одном месте
storage файлы / SQLite: сценарии, планы, логи прогонов
```

**Жёсткое правило:** `core` не импортирует ничего из `api` и `web`. Ядро запускается через CLI и живёт без веба. Это страховка на случай, если веб-слой отстанет.

### Упаковка

Docker: два образа (api, web), `docker compose up` поднимает всё одной командой на чистой машине без ручных шагов. Жюри запускает решение само.

## 3. Ограничения по стеку

Вынесено отдельным разделом намеренно: это рамки, за которые не выходим без явного обсуждения командой.

### Разрешено и предпочтительно

| Слой | Технологии |
|---|---|
| Ядро | Python 3.11+, NumPy, Shapely (GEOS), pyproj |
| Бэкенд | FastAPI, pydantic v2, uvicorn |
| Фронтенд | React 18, TypeScript, Vite, Leaflet |
| Хранилище | Файлы (JSON) и/или SQLite |
| Упаковка | Docker, docker compose |
| Тесты | pytest |
| Рельеф (опционально) | rasterio, GeoTIFF |

### Запрещено или не используется

- **Сервисы Google** (Maps, Earth Engine, любые API с ключом Google). Подложка — OpenStreetMap с обязательной атрибуцией «© OpenStreetMap contributors» и офлайн-фолбэком закешированных тайлов.
- **Celery, Redis, RabbitMQ** — долгие расчёты выполняются фоновой задачей внутри процесса API с поллингом статуса.
- **PostGIS как обязательная зависимость** — в ТЗ он «по желанию», пространственные запросы поверх множества сценариев проекту не нужны.
- **Авторизация, роли, многопользовательский режим, миграции БД** — не в объёме.
- **Тяжёлые CSS-фреймворки и UI-киты** сверх необходимого.
- **Библиотеки с несвободными или вирусными лицензиями.** Только permissive (MIT / BSD / Apache 2.0) и совместимые.
- **Обращения к внешним API в рантайме демонстрации.** На площадке может не быть интернета. Все внешние данные (тайлы, рельеф) скачиваются заранее и лежат в репозитории или томе.

### Под вопросом, решается отдельно

- OR-Tools — только как опциональная альтернатива собственной эвристике для сравнения, не как основа. Кастомная стоимость с ветром, многовылетностью и разнотипным флотом плохо ложится на стандартные callback'и.
- WebSocket вместо поллинга — только если останется время после закрытия функциональности, дающей баллы.

## 4. Доменная модель

| Тип | Суть |
|---|---|
| `Scenario` | Область съёмки, запретные зоны, границы воздушного пространства, площадки взлёта и резервные, тип съёмки, требования к качеству, ветер, состав флота |
| `Vehicle` | Тип (самолётный / мультиротор), крейсерская скорость, автономность, допустимый ветер, радиус разворота, совместимые нагрузки, доля неснижаемого резерва заряда |
| `SurveyPlan` | Высота, шаг галсов, скорость съёмки, перекрытия — результат сенсорной модели |
| `Strip` | Один галс: геометрия, длина, высота, скорость |
| `Leg` | Участок полёта с фазой: взлёт / набор / транзит / галс / разворот / снижение / посадка |
| `Sortie` | Один вылет одного борта: площадка, последовательность `Leg`, длительность, израсходованная энергия |
| `Mission` | Набор вылетов, метрики (makespan, суммарный налёт, дистанция), предупреждения валидатора |

Схемы описываются pydantic-моделями в `core/schemas.py` и экспортируются в JSON Schema, из которой генерируются TypeScript-типы для фронтенда.

## 5. Инварианты, которые нельзя нарушать

Эти правила — источник самых дорогих и самых незаметных ошибок в проекте. Любой код, их нарушающий, считается сломанным независимо от того, проходят ли тесты.

1. **Вся геометрия считается в метрической проекции.** Географические координаты (WGS84) живут только на границах системы: на входе из сценария и на выходе в экспорт. Расчёты в градусах дают неверные расстояния и площади, ошибка тихая.
2. **`core` не знает про веб.** Ни одного импорта из `api`. Ядро должно запускаться как `python -m core.cli`.
3. **`core/schemas.py` — общий контракт.** Изменение схемы ломает сразу несколько параллельных потоков работы. Правка только с явной отметкой в `current_state.md`.
4. **Направление ветра задаётся в метеорологической конвенции** — откуда дует. Перепутанный знак даёт зеркальный план, и это обнаруживается только на демонстрации.
5. **Физические константы живут только в `core/assumptions.py`**, каждая с комментарием об источнике. Магические числа в коде расчётов запрещены. Этот файл механически превращается в раздел «известные ограничения» документации, который требуется по ТЗ.
6. **Технические характеристики БВС не выдумываются.** Они берутся из `data/vehicles.yaml`, заполняемого командой из официальных источников. Если характеристики неизвестны — это помечается как пробел, а не заполняется правдоподобным числом.
7. **Время полёта не считается как «длина делить на скорость».** Учитываются фазы полёта, ветер, развороты и резерв заряда.
8. **Baseline-алгоритм (равномерное деление области) никогда не удаляется.** Он всегда даёт результат и служит точкой сравнения для доказательства эффективности.

| E5 | Транзит с обходом запретных зон (граф видимости) | P1 |
| E6 | Распределение по флоту и оптимизация (baseline → эвристика → локальный поиск) | P0 |
| E7 | Валидация выполнимости и безопасности плана | P1 |
| E8 | Экспорт полётных заданий (KML, GeoJSON) | P0 |
| E9 | API и сервисный слой | P0 |
| E10 | Редактор сценария | P0 |
| E11 | Визуализация и анализ результата | P0 / P1 |
| E12 | Доказательство эффективности (baseline, бенчмарк, Парето) | P1 |
| E13 | Документация, демо, защита | P0 |

**Не режется при урезании объёма:** переключение критерия оптимальности (E6) и сравнение с baseline (E12). Без них решение выглядит как рисовалка галсов, а не как сервис оптимизации.

## 7. Внешние источники

### Данные о технике

Официальные документы с техническими параметрами, ссылки из исходного PDF задания (`5. Геоскан.pdf`, раздел 6 «Ресурсы»):
- Геоскан 201 — борт самолётного типа, катапультный старт, парашютная посадка, минимальный радиус разворота. https://download.geoscan.ru/site-files/201/Geoscan_201_Manual.pdf
- Геоскан 801 — мультиротор. https://download.geoscan.ru/site-files/801/Geoscan_801.pdf?v2
- Геоскан Gemini — квадрокоптер, время полёта около 40 минут, площадь съёмки до ~1 км² за вылет. https://download.geoscan.ru/site-files/gemini/Gemini_Specs_EN_RUS.pdf?v2

Характеристики переносятся в `data/vehicles.yaml` с указанием источника для каждого параметра.

### Референсное ПО (для понимания форматов и UX)

- Geoscan Planner — https://www.geoscan.ru/ru/software/geoscan_planner
- Mission Planner (ArduPilot) — формат `.waypoints`. https://ardupilot.org/planner/docs/mission-planner-installation.html
- QGroundControl — формат `.plan` (JSON). https://qgroundcontrol.com/

### Картографическая подложка

- OpenStreetMap, тайлы `tile.openstreetmap.org`, лицензия ODbL, обязательная атрибуция.
- Публичный тайл-сервер имеет строгую политику использования и rate limit — для демонстрации тайлы тестовых областей кешируются заранее и отдаются локально.

### Рельеф (опционально, для LiDAR и геофизической съёмки)

- SRTM (~30 м), Copernicus GLO-30 (~30 м) — GeoTIFF, скачивается по bbox заранее, в рантайме не запрашивается.
- В OpenStreetMap данных о рельефе нет, это отдельный источник.

### Спецификации форматов

- GeoJSON — RFC 7946
- KML — спецификация OGC; критично корректно выставить режим высоты (`clampToGround` / `relativeToGround` / `absolute` дают три разных смысла)

### Открытые вопросы к организаторам

Ответы меняют объём эпиков E3, E4 и E6. До получения ответов принимаются допущения, фиксируемые в `assumptions.py`:
1. Точки взлёта задаёт пользователь или сервис подбирает их сам? Нужна ли поддержка нескольких вылетов одного борта со сменой батареи?
2. Будут ли эталонные тестовые сценарии в фиксированном формате? Есть ли требования к схеме экспорта и совместимости с конкретной наземной станцией?
3. Насколько детально моделировать ветер (константа или профиль), рельеф (нужна ли ЦМР) и специфику самолётного типа (радиус разворота, старт с катапульты, снос при посадке)?

## 8. Что нужно сгенерировать на основе этого брифа

### 8.1 `AGENT.md` — инструкции для агентной разработки

Документ адресован агенту, который пишет код в этом репозитории. Должен содержать:

- **Контекст и архитектурный инвариант** — конвейер стадий, границы слоёв, правило «core не знает про веб».
- **Карту репозитория** — какой модуль за что отвечает, куда класть новый код, куда точно не класть (геометрические расчёты в слое API — типичная ошибка).
- **Инварианты из раздела 5** этого брифа в виде явного чек-листа, который агент проверяет перед завершением работы.
- **Правила работы с контрактом** — `core/schemas.py` менять только осознанно, с отметкой в `current_state.md`; при изменении схемы перегенерировать TypeScript-типы.
- **Правила для параллельной агентной работы:** одна сессия — один эпик — одна ветка; не трогать модули за пределами эпика; если для работы нужен ещё не реализованный модуль — писать заглушку с правдоподобными данными и явным `TODO`, а не блокироваться и не переписывать чужую зону.
- **Обязательные шаги перед завершением задачи:** прогон тестов, прогон линтера/форматтера, прогон CLI на тестовых сценариях из `scenarios/`, обновление `docs/current_state.md`.
- **Что запрещено делать самостоятельно:** выдумывать технические характеристики БВС, добавлять зависимости вне раздела ограничений по стеку, вводить внешние API-вызовы в рантайме, менять целевую функцию оптимизации без явной задачи, удалять baseline-алгоритм.
- **Требования к коду:** типизация, докстринги для публичных функций стадий с указанием единиц измерения (метры, секунды, радианы), детерминированность (фиксированные seed'ы), отсутствие магических чисел вне `assumptions.py`.
- **Формат отчёта о работе:** что сделано, какие допущения приняты, что осталось незакрытым, какие новые пробелы обнаружены.

### 8.2 `CLAUDE.md` — рабочий контекст

Короткий файл в корне, который читается автоматически в начале сессии. Не дублирует `AGENT.md`, а указывает на него и даёт оперативное:

- Одно-два предложения о проекте.
- Ссылки: `AGENT.md`, `PROJECT_BRIEF.md`, `docs/architecture.md`, `docs/epics.md`, `docs/current_state.md`.
- Команды: установка, запуск через docker compose, прогон тестов, прогон CLI на тестовом сценарии, генерация TypeScript-типов.
- Три-пять самых критичных инвариантов одной строкой каждый.
- Правило: начинать сессию с чтения `docs/current_state.md`, заканчивать его обновлением.

### 8.3 `docs/current_state.md` — текущее состояние проекта

Живой документ, обновляемый в конце каждой сессии. Структура:

- **Статус по эпикам** — таблица: эпик, состояние (не начат / в работе / готов), что конкретно работает, что заглушка.
- **Что работает end-to-end прямо сейчас** — честное описание сквозного пути, без «почти готово».
- **Заглушки и временные решения** — список с указанием, какой эпик их закроет.
- **Принятые допущения** — те, что ещё не перенесены в `assumptions.py`, и те, что ждут ответа организаторов.
- **Известные проблемы и долги.**
- **Журнал изменений** — дата, что изменилось, особо отмечать правки контракта `core/schemas.py`.

Первая версия файла создаётся сразу и описывает состояние «репозиторий создан, код не написан» — чтобы документ существовал с первого дня и обновлялся, а не создавался задним числом.

### 8.4 `docs/external_sources.md`

Раздел 7 этого брифа, вынесенный отдельным файлом, с заполненными ссылками и указанием, какие данные скачаны локально и куда положены.
